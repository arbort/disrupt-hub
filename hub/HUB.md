# HUB.md — Disrupt-Hub: контентный движок

Контекст-файл стрима. Читается целиком агентом `hub-writer` перед любой
задачей. Заведено 2026-09-12 — идея Арсения, согласована с продактом
Дизрапта.

---

## Проблема и идея

Дизрапт-продукты теряют пользователей отчасти потому, что те не знают всех
способностей тулов — не понимают, чем конкретно продукт полезен в их работе
или жизни. Это бьёт по удержанию, а удержание — главный рычаг среднего DAU
(см. `../DISRUPT.md`).

Алиса решает соседнюю задачу ПромптХабом (`alice.yandex.ru/prompthub`), но
только вокруг LLM-части — библиотека промптов, не бизнес-кейсов. Готовых
статей о реальном применении там нет.

**disrupt-hub.ru** — платформа с E2E-статьями и гайдами об использовании
продуктов Дизрапта в реальных рабочих и жизненных сценариях: скрины,
настройки, промпты, а не список функций. Фильтр по продукту. Часть статей —
свой ИИ-движок, часть — публикации пользователей. Лучшее тиражируется во
внешку (Dzen, VC, Habr) через партнёрский подход, который ещё предстоит
согласовать.

**Отличие от ПромптХаба:** не библиотека промптов вокруг одной LLM, а
библиотека кейсов вокруг девяти разных инструментов (десктоп-приложения,
TG-боты, браузерный агент, публичная витрина research-конвейера) — ближе к
связке «блог кастомер-стори + Zapier-style use-case библиотека», чем к
маркетплейсу промптов. Состав — см. «Решения от 2026-09-12» ниже.

**Пересмотрено 2026-09-12.** Изначально контент и платформа были разведены
по аналогии с таблицей «Зоны ответственности» в `../DISRUPT.md` (платформа —

платформы в рамках этой же сессии — первая версия сайта собрана и лежит в

(хостинг, домен, форма приёма UGC) **не назначен** — не читать это как
окончательный перенос зоны на администратора, только как факт, кто собрал v1.

| Зона | Кто отвечает |
|---|---|
| Контентный движок: семантика, темы, ТЗ, черновики статей, QC, UGC-модерация, синдикация | **Администратор** (Арсений + `hub-writer`) |

| Админка контента + SEO-инфраструктура сайта (canonical/OG/JSON-LD/sitemap) | **Администратор**, собрана 2026-09-13, см. ниже |
| Форма приёма UGC, домен `disrupt-hub.ru`, долгосрочная техподдержка бакетов/функции | **Не назначено** — открытый вопрос |

## Платформа v1

Исходники — `site/` (Astro, статическая сборка, деплой-ready на Vercel).
Дизайн — язык `deslop` (github.com/mishanaer/deslop): токены скопированы в
`site/src/styles/deslop/`, тёмная тема включена жёстко (не по системной
теме посетителя), что осознанно расходится с правилом «независимый
брендинг» — то правило про рекламные креативы продуктов, для этой публичной
поверхности сделано отдельное исключение решением Арсения.

**Контент не дублируется.** Astro Content Collection (`site/src/content.config.ts`)
читает Markdown прямо из `articles/` этой же папки через `glob()`-loader —
не копия, не symlink. `hub-writer` пишет статьи туда же, куда писал всегда;
рендерится в проде только то, что имеет во фронтматтере `status: published`.

**Обязательный фронтматтер Stage 3** (новое требование к черновику статьи,
без него Astro не соберёт файл в коллекцию):

```yaml
---
title: "Заголовок"
product: tool        # слаг из site/src/data/products.ts
topicId: tool-5        # добавлено 2026-09-13 — "<product>-<номер темы в topics/<product>-backlog.md>"
status: draft         # idea | brief | draft | qc | published
h1: "H1 на странице"
metaTitle: "..."
metaDescription: "..."
date: 2026-09-12
---
```

**`topicId` обязателен с 2026-09-13.** Единственная связь между написанной
статьёй и строкой бэклога — дашборд «Реестр тем» в админке (см. «Админка и
SEO-инфраструктура») сопоставляет их именно по этому полю, не по совпадению
заголовка (заголовок статьи почти всегда переформулирован против темы в
бэклоге). Статья без `topicId` не пропадает — просто попадает в реестре в
раздел «не привязано к бэклогу», и придётся сверять вручную. И `hub-writer`,
и облачная routine обязаны проставлять это поле при написании — для routine
это зашито прямо в её промпт (см. `project_disrupt_hub_autonomous_routine`
в памяти сессии).

**Задеплоено 2026-09-12** на Yandex Object Storage (грант Арсения) —
https://disrupt-hub-deploy.website.yandexcloud.net/. HTTPS работает на
общем домене бакета из коробки. Кастомный домен `disrupt-hub.ru` не
подключён — нужен CDN, отдельный шаг. Передеплой — `npm run deploy` в
`site/`. Полные детали хостинга, что не реализовано (форма UGC, домен) —
`site/README.md`.

## SEO-команда Сбермаркетинга — контекст, не пайплайн

Арсений прощупал платную команду SEO-аналитики Сбермаркетинга. Их обычный
процесс (для справки, хорошая практика сама по себе):

```
разговор о продукте (что раскрывать, что нет)
  → их аналитика и подбор тем → мы утверждаем темы
  → они готовят ТЗ → мы пишем статьи → отправляем на проверку соответствия ТЗ
  → мы публикуем → они проверяют повторно → начинается отслеживание
```

Их урезанное предложение «только по контенту» (без остальных работ по SEO):

- сбор семантики до **20 тем**
- ТЗ на **10–15 текстов**
- мета и H1 к ним
- **итоговая проверка** (соответствие ТЗ)

**Решение:** это предложение в пайплайн не встраивается. Пайплайн ниже
спроектирован как полностью автономный — `hub-writer` сам закрывает
семантику → ТЗ → черновик → QC. Агентство остаётся опцией на будущее:
если понадобится всплеск мощности (например, быстро расширить бэклог сверх
собственных возможностей), к ним можно вернуться на этих же условиях, не
меняя структуру процесса — их ТЗ ложится в тот же формат Stage 2.

Гейт «темы утверждает Арсений до ТЗ» **сохранён** из их процесса — это
хорошая практика вне зависимости от того, кто пишет ТЗ.

**Прецедент из соседнего SEO-контура giga.chat (2026-09-12).** Арсений
прислал реальный рабочий xlsx, который команда SEO giga.chat вела с
агентством 10 месяцев (окт. 2025 — авг. 2026, 253 строки контента + отдельный
лист технических задач). Извлечено и применено к реестру статей (Google Doc):
разведены «URL рекомендованный» и «URL фактический» (SEO-план по слагу почти
всегда расходится с тем, что реально сделал разработчик), статусная лестница
после черновика сделана многоступенчатой (согласовано → размещено → внедрено
— это разные события, не один флаг «опубликовано»), добавлен терминальный
статус «отклонено» с причиной (тема может умереть, не только дойти до
публикации). Сознательно НЕ скопированы колонки «дедлайн», «копирайтер»,
«редполитика», «ТЗ на усиление» — в прецеденте они провисели пустыми весь
срок: не заводить поле под процесс, которого ещё нет.

Лист с техническими SEO-задачами (редиректы, canonical, robots meta, XML
sitemap, микроразметка, перелинковка, Core Web Vitals) сохранён отдельно —
`platform-technical-seo.md` в этой же папке. Это работа для того, кто будет
технически собирать disrupt-hub.ru, не для контентного движка.

## Стилистика и подбор тем giga.chat — второй проход (2026-09-14)

Первый проход по тому же xlsx (выше) разобрал только процесс — колонки,
статусы, разведение «URL рекомендованный/фактический». Здесь — второй
проход по содержимому: живой аудит 7 опубликованных статей на
giga.chat/help/articles и giga.chat/catalog плюс полный список 253 тем листа
«копирайтинг» за окт. 2025 — авг. 2026. Задача — вытащить из чужого 11-месячного
production-цикла то, что усиливает голос и структуру статей хаба, и явно
отделить то, что переносить нельзя.

### Что переносим

| Находка у giga.chat | Механика | Как встроено в disrupt-hub |
|---|---|---|
| Бренд-упоминание в первом абзаце, не только в CTA | Каждая статья — «Как создать ИИ-ассистента, подробно разбираем в статье [GigaChat]» — гиперссылка на продукт уже в первых 2-3 предложениях, органично, без рекламного тона | Stage 2 (ТЗ): аутлайн обязан указывать, в каком предложении интро упоминается продукт со ссылкой на его лендинг. Stage 4, чек-пойнт 1: отсутствие ссылки на продукт в интро — повод вернуть на доработку |
| Заголовок для поиска ≠ заголовок на странице | `<title>` длиннее и с брендовым суффиксом («Промпт для нейросети: что это такое и как правильно составить промт – примеры и правила написания \| ГигаЧат»), H1 короче и в разговорной вопросной форме («Что такое промпт?») | Фронтматтер уже разводит `h1`/`metaTitle` — формализуем разницу: `h1` = вопрос пользователя как он есть в голове, без брендового хвоста; `metaTitle` = `h1` + уточнение или отличие от конкурентной выдачи, не дословный дубль |
| Двухголосая подача | Редакторская проза сдержанная, без восклицаний; но живые цитаты вывода модели (пример промпта → пример ответа) сохраняют тот тон, который выдал сам сервис, вплоть до «Твой путь в IT начинается здесь!» | Правило голоса: текст статьи — ровный, без литературных красивостей (см. `feedback_headline_tone`); но если в статье есть блок реального вывода продукта — его нельзя «причёсывать» под редакторский тон, это исказит артефакт. Цитата продукта живёт своим голосом |
| Скобочная расшифровка терминов при первом употреблении | «(поисковую оптимизацию) SEO», «(атака, направленная на перегрузку сайта) DDoS-атака» — сразу ловит и полную формулировку, и аббревиатуру как отдельные поисковые фразы | Добавлено в чек-лист Stage 4, чек-пойнт 1: первое употребление незнакомого термина/аббревиатуры — с кратким пояснением в скобках, а не с отдельной сноской |
| «Каталог промптов»: страница = вопрос + живой ответ продукта, без вступительной прозы | `giga.chat/catalog/streak-free-windows` — H1 это сам промпт, тело — дословный ответ сервиса, ничего лишнего. Дешёвая в производстве форма, закрывающая длинный хвост конкретных запросов | Новый лёгкий подтип статьи на Stage 3 — **«живой пример»**: реальный сценарий/промпт → реальный скрин или вывод продукта → 2-4 предложения контекста, без лонгрида. Несёт тот же жёсткий артефакт-критерий, что и E2E-статья, просто короче. Выбор формата (лонгрид vs живой пример) — решение Stage 2, не Stage 3 |
| Соседний высокочастотник как приманка, продукт — как ускоритель задачи | Статьи про Tilda, Ozon, VS Code не про GigaChat формально, но ближе к концу всегда возвращают: «вот как GigaChat ускоряет именно эту задачу» | Формализация уже действующей логики хаба: тема может быть построена вокруг задачи, которая сама по себе не про продукт (`как выгрузить отчёт в Excel` для Мультитула), если статья всё равно несёт реальный артефакт, показывающий продукт внутри этой задачи. Это не новое исключение из «без артефакта не публикуем» — это форма, в которой артефакт может появиться |
| Сезонный контент-календарь | Темы про 23 февраля/8 марта/майские планировались за 4-6 недель до даты | Дополнительная (необязательная) ось модификатора в Stage 1 seed × modifier — сезонность/календарный повод, только если у продукта есть органическая привязка к дате (не заводить искусственно) |
| Регулярный рерайт по факту угасания | Отдельный SEO-документ «Анализ необходимости рерайта» — рерайт не разовая акция, а стоящая в календаре ревизия | Правило на будущее: когда наберётся ≥ 20 опубликованных статей с ≥ 3 месяцами истории, завести квартальную ревизию кандидатов на рерайт по факту органики/устаревания фактуры. Пока сайт не откручен — не применимо, зафиксировано как триггер, не как задача |

### Что не переносим

**Пивот в полностью небрендовые темы ради объёма.** После января 2026 в
бэклоге giga.chat всё чаще попадаются темы, вообще не связанные с ИИ:
рецепт блинов, горячие клавиши VS Code, что такое IP-адрес, комбинаторика,
прокрастинация — статьи получают связку с продуктом в лучшем случае одной
фразой в конце. Это работает у giga.chat, потому что домен огромного
доверия и рекламного бюджета конвертирует любой органический заход в узнаваемость
одного мега-продукта. У disrupt-hub — новый домен без истории индексации перед
девятью независимыми small-продуктами: публиковать объём тонких страниц без
реального артефакта на старте — то самое scaled content abuse, от которого
жёсткое правило хаба уже защищает. Граница не двигается: **без реального
продуктового артефакта — не публикуем**, вне зависимости от того, что себе
может позволить домен с другим порядком доверия поисковика.

|---|---|---|
| Контент-хаб = pillar + cluster. **Продуктовый** контент (реальные скрины/workflow) устойчивее к копированию AI/конкурентами, чем общеобразовательный | [w3era](https://www.w3era.com/blog/seo/saas-seo-complete-guide/), [quoleady](https://www.quoleady.com/product-led-content/) | Правило: каждая статья обязана нести реальный артефакт продукта — скрин, настройку, промпт. | Бриф = кластер интентов, не одно ключевое слово; шапка брифа фиксирует intent/формат/глубину vs конкуренты | [digitalapplied](https://www.digitalapplied.com/blog/content-brief-template-2026-seo-writer-handoff-framework) | Структура ТЗ, Stage 2 |
| Аналоги: OpenAI/Claude Cookbook — официальный движок + вклад комьюнити, организация по use-case, не по продукту-источнику | [обзор Anthropic Cookbook](https://beginnersinai.org/anthropic-cookbook/) | Подтверждает гибридную модель «свой движок + пользовательские статьи» как рабочую, не экспериментальную |

## Стандарт письма: SEO-структура + анти-слоп (2026-09-17)

Снято по прямому запросу Арсения при переводе хаба в боевой режим — свод
внешних SEO-гайдов агентств/Google/Яндекса и публичных методик
«очеловечивания» AI-текста, обязателен к применению на Stage 3 (черновик) и
проверке на Stage 4 (QC, чекпойнт 1).

### SEO-структура статьи

| Правило | Конкретика | Источник |
|---|---|---|
| Заголовки | Один H1 (короткий вопрос читателя, см. «Стилистика... giga.chat» выше). H2 — независимые подтемы, H3 — детали внутри подтемы. По одним заголовкам читатель должен понять структуру всей статьи | Ahrefs, TexTerra |
| Открытие | Первый абзац — прямой ответ/факт/реальный артефакт, без раскачки («в этой статье мы рассмотрим», «в современном мире»). Это же требование усилено поведением Яндекса (см. ниже) | Orbit Media, TexTerra |
| Абзацы и списки | Абзац ≤4 строк. Список — если 3+ параллельных пункта, не раньше | Orbit Media |
| Плотность ключевых слов | **Не метрика.** Официально опровергнуто Google (Cutts 2011, подтверждено Mueller) — не считать и не таргетировать. Вместо этого: точная фраза темы — в metaTitle/H1/первом абзаце; 5–8 семантически связанных фраз органично по тексту | Google, Rankability |
| Мета-теги | `metaTitle` 40–60 символов (макс. CTR-диапазон, Backlinko, анализ 4М выдач), ключевая фраза ближе к началу. `metaDescription` 150–160 символов, формулирует выгоду читателю, не список ключей | Backlinko, TexTerra |
| Длина статьи | **Не фиксируется числом слов.** Решает глубина покрытия кластера интентов (Stage 2), не таргет объёма — искусственное растягивание запрещено. «2000 слов — идеал» — развенчанный миф | Ahrefs, Search Engine Land |
| Внутренние ссылки | 5–10 на статью (не считая ссылки на продукт в интро, см. giga.chat-приём выше): на карточку продукта + 1–2 родственные статьи хаба того же продукта/кластера. Анкор описывает пункт назначения, не повторяется дословно | Semrush, TexTerra |
| Поведенческие факторы Яндекса | **Внешний ориентир, не наш факт** — Яндекс формулу не публикует, оценки из SEO-комьюнити (не подтверждены официально): поведенческие факторы весят в ранжировании Яндекса заметно больше, чем в Google, первый экран должен закрывать интент сразу — иначе быстрый возврат в выдачу («pogo-sticking») бьёт по позиции сильнее, чем в Google | Trigub, Kokoc (RU SEO-комьюнити) |

**Пре-паблиш гейт (объединение чек-листов Google/TexTerra/seohead.pro)** —
добавлено в Stage 4, чекпойнт 1: заголовки образуют законченную карту статьи →
интент закрыт с первого экрана → структура без «воды» и без пустых
переходных фраз → факты проверяемы (см. «жёсткие правила») → мета
написаны вручную под смысл, не автогенерацией.

### Семантический срез перед ТЗ (Stage 2)

Данные уже собираются в `admin/scripts/topic-frequency-details.json` (широкая
частотность + топ-10 похожих фраз `results` + смежные `associations`, см.
«Админка и SEO-инфраструктура» выше) — раньше использовались только для
приоритизации темы в реестре. **С 2026-09-17 те же данные обязательны и для
самого ТЗ**, не только для сортировки:

1. Для утверждённой темы — открыть её карточку в `topic-frequency-details.json`.
   Если темы там нет (входит в непокрытые ~28 из 90) — прогнать `wordstat-check.py`
   точечно по фразе из `topic-phrases.tsv` (или подобрать новую фразу, если
   её там нет) по существующей конвенции среды (точечно, не валом).
2. Из `results` (топ похожих) вручную отобрать 5–8 фраз, реально релевantных
   теме — **не все подряд**: `associations` шумят по общему слову, не по
   смыслу (пример из практики: «калории по фото» подтянула «бпла фото» —
   общее слово «фото», к теме отношения не имеет). Исключённые нерелевантные
   варианты фиксировать в ТЗ отдельной строкой, чтобы решение было видно,
   а не терялось.
3. Отобранные фразы — в ТЗ явным списком (кластер интентов, который уже
   требуется в Stage 2, получает конкретное наполнение, а не остаётся
   абстрактным пунктом).

**Зона ответственности — обновлено 2026-09-17, вечер: теперь и `hub-writer`,
и облачная routine.** Изначально это было ограничено интерактивным путём —
у routine не было ни доступа к `admin/` в узком контекст-репозитории, ни
сетевого доступа к Wordstat API. Оба ограничения сняты по решению Арсения:

- В узкий контекст-репозиторий добавлен `hub/admin/scripts/topic-phrases.tsv`
  (только этот файл — маппинг topicId → поисковая фраза, без секретов; не
  весь `admin/`, там остаются `.env.local` и код Cloud Function).
- В allowlist окружения routine добавлен домен `searchapi.api.cloud.yandex.net`
  (Custom network access, тот же список, где уже стоял `functions.yandexcloud.net`).
- Ключ `YANDEX_AI_API_KEY` встроен в промпт routine тем же способом, что и
  `ADMIN_SECRET` — хранится в конфигурации routine на стороне Anthropic, не
  в git.

Routine теперь перед черновиком делает один запрос к Wordstat `topRequests`
по фразе темы (из `topic-phrases.tsv`, либо сама коротко формулирует фразу
из заголовка бэклога, если темы там нет), отбирает 5–8 релевантных фраз из
`results`, явно исключая шумные совпадения по общему слову, и вплетает их в
статью. **Не жёсткий гейт** — Wordstat нестабилен (403 флейк, часовая квота
429), при отказе routine пишет статью без семантических данных и отмечает
это в отчёте, не блокирует прогон целиком.

### Анти-слоп: человеческий язык

Источники: [Wikipedia:Signs of AI writing](https://en.wikipedia.org/wiki/Wikipedia:Signs_of_AI_writing),
[Википедия:Признаки сгенерированности текста](https://ru.wikipedia.org/wiki/Википедия:Признаки_сгенерированности_текста)
(русскоязычная версия, независимый список, не перевод), машиночитаемый список
канцелярита [slop-gate/russian.json](https://github.com/hwajongpark/slop-gate).
Прогонять текст по списку перед сдачей на Stage 4 — не автоматическая замена,
а редакторская вычитка.

**Канцелярит (следствие плохого перевода/AI-регистра, не литературная норма):**

| Что резать | Чем заменить |
|---|---|
| «является/являются» | тире или «это» |
| «осуществить/осуществлять» | прямой глагол («зарегистрироваться», «сделать») |
| «в целях» | «чтобы» |
| «в случае возникновения» | «если» |
| «следует отметить, что» | вырезать целиком, начать с сути |
| «надлежащим образом» | «правильно» |
| «в соответствии с» | «по» (закону/правилам) |
| «было принято решение» | назвать, кто решил («мы решили») |
| «данный» (не про данные) | «этот» |

**Дидактическое хеджирование — вырезать целиком, не смягчать:** «важно/
критично/необходимо отметить», «стоит учесть/запомнить», «значения могут
варьироваться».

**Инфляция значимости и ложная агентность** (факт или продукт не может
«подчёркивать» или «символизировать» — только человек): «играет важную/
ключевую роль», «подчёркивает важность», «служит напоминанием», «поворотный
момент», «неизгладимый след».

**Промо-надувательство:** «богатый функционал», «яркий пример», «может
похвастаться», «расположенный в самом сердце», «потрясающий результат».

**Диалоговые утечки модели — прямой след чат-бота, вырезать полностью, не
редактировать:** «безусловно», «несомненно», «конечно», «вы абсолютно
правы», «надеюсь, это было полезно», «сообщите, если нужно уточнить».

**Клише-параллелизмы:** «не только X, но и Y», «это не просто X — это Y»,
«Y, а не X» как заезженная конструкция. Не путать с «правилом трёх» (три
параллельных примера подряд) — тоже маркер, если это структурный тик, а не
осознанный приём.

**Типографика:** тире с пробелами через каждое второе предложение — тик
модели, не стиль. Использовать по необходимости пунктуации, не как связку.

**Правило анти-сверхкоррекции** (дословно из практики де-слопификации —
[haidrrrry/humanize-ai-writing](https://github.com/haidrrrry/humanize-ai-writing)):
одно случайно найденное слово из списка — не повод калечить предложение или
резать реальную информацию. Цель — не допустить **кластеров** примет, сохранив
факты, цифры, имена и позицию автора. Хаб уже требует «два голоса» (см.
«Стилистика... giga.chat» выше) — цитата реального вывода продукта этому
списку не подчиняется, её тон — тон самого продукта, не редактора.

## Семантика вперёд тем: методология SEO-агентства giga.chat (2026-09-17)

Арсений скачал реальный рабочий комплект SEO-агентства, ведущего giga.chat
10+ месяцев: семантическое ядро с расчётом P/traf (`giga_chat_семантическое_
ядро_общее_c_Ptraf...xlsx`, 8 листов), пять готовых ТЗ на копирайт/рерайт
статей, отчёт о технической рекомендации (пагинация раздела «Промпты») и
помесячный SEO-дашборд (апрель 2026). Разобрано подробно — что переносим в
саму механику отбора тем и структуру ТЗ, не только в стиль (стиль и голос
уже разобраны в «Стилистика и подбор тем giga.chat» выше).

**Диагноз, который поставил Арсений: у нас порядок перевёрнут.** Агентство
сначала строит семантическое ядро (тысячи фраз → группы → расчёт трафика на
группу), и только из групп с доказанным спросом предлагает страницы/темы.
У нас Stage 1 — это брейнсторм по методу seed×modifier, а Вордстат
подключается **после**, точечно и по желанию, часто оставляя `[TBD]`
(см. `tool-backlog.md`: «Частотность не снималась по Вордстату — проверяется
точечно, после того как темы отобраны»). Тема может годами простоять без
реального спроса просто потому, что никто не удосужился её проверить раньше
утверждения. Это меняется ниже — не косметика, а порядок шагов Stage 1.

### Реальный пайплайн агентства (что нашли)

Восемь листов xlsx образуют цепочку, а не независимые таблицы:

```
Семантика (сырое ядро: фраза → [WS] широкая/точная, позиция Я/Google,
           P/traf MAX/текущий/Loss на фразу И на группу)
  → Предлагаемые страницы (свёртка по группам, сортировка по P/traf Loss
     группы — где именно теряется больше всего трафика)
  → Контент-план (приоритет 1/2/3, тип текста Новый/Рерайт/Промпт, статус
     согласования, период размещения)
  → ТЗ на копирайт/рерайт (одна страница = один документ: H1/Title/
     Description, конкуренты, аутлайн H2/H3, таблица ключей с мин/макс
     вхождений, LSI-фразы, чек-лист пост-вычитки)
  → Теги (H1/Title/Description начисто, когда текст готов)
  → помесячный дашборд (Сводка/Качество/Позиции/Популярные страницы/
     Результаты — успех измеряется снижением P/traf Loss по кластеру, не
     числом опубликованных статей)
```

**P/traf** — расчётная метрика: `P/traf MAX` = верхняя граница трафика при
позиции №1 (широкая частотность × CTR-кривая по позиции), `P/traf текущий` =
трафик на фактической позиции, `P/traf Loss` = MAX − текущий, то есть размер
упущенной возможности. Считается и на фразу, и свёрнуто на группу/страницу —
именно это число сортирует «Предлагаемые страницы» и решает, какая страница
важнее следующей, а не субъективное ощущение «эта тема интереснее».

### Что переносим буквально

| Находка | Как встроено в хаб |
|---|---|
| Семантика собирается **до** предложения тем, не после | Новый порядок Stage 1 — см. ниже |
| P/traf Loss = приоритет страницы, не брейнсторм | Новая колонка-оценка в бэклоге, заменяет непрозрачную часть текущего «Балла» реальной прикидкой трафика (см. ниже) |
| ТЗ = один документ на страницу с конкурентами + таблицей ключей с мин/макс | Расширена структура Stage 2, materializация файла обязательна (было — только «в голове» у routine) |
| Плотность ключа — потолок, не таргет («не больше 1 вхождения на 300 знаков») | Добавлено в таблицу ключей ТЗ — это ограничение сверху, согласуется с уже действующим правилом «плотность не метрика» из «Стандарт письма» |
| Гейт согласования ДО производства — у агентства это отдельный шаг «Статус согласования» до того, как копирайтер вообще получает ТЗ | Новый гейт: ТЗ утверждается Арсением, прежде чем начинается черновик — см. «Двухступенчатый гейт» ниже |

### Что не переносим

Файлы giga.chat используют платные сервисы, которых у хаба нет: Топвизор
(трекинг позиций по обоим движкам ежедневно), сервис оценки мин/макс вхождений
по анализу топ-10 конкурентов (вероятно Just-Magic/Rush Analytics-класс),
Advego/Orfogrammka/Content-watch/Тургенев для пост-проверки текста. Хаб — не
воспроизводит эти инструменты, а адаптирует их роль: там, где нужна позиция
в выдаче — у нас `P/traf текущий` = 0 почти везде (сайт без истории
индексации), поэтому `P/traf Loss ≈ P/traf MAX`; там, где нужен подсчёт
вхождений топ-10 — у нас плотность используется только как верхний потолок
через уже существующий анти-слоп чек-лист, не как измеряемая программой
метрика.

### P/traf-оценка для хаба (адаптация)

Без данных о реальной позиции в выдаче (сайт только запущен) точный P/traf
Loss посчитать нельзя. Рабочая прикидка — **внешний ориентир, не наш факт**,
эмпирическая пропорция, замеченная в самом файле giga.chat (пример:
WS=17 908 → P/traf MAX=2396,5, то есть ≈13% от широкой частотности —
это ближе к позиции 2-3, реалистичной цели для нового домена, а не к позиции
№1):

```
P/traf-оценка ≈ Широкая частотность (Wordstat) × 0.13
```

Пока ни одна статья хаба не проиндексирована и не ранжируется, `P/traf
текущий` = 0 для всех тем без исключения — значит P/traf-оценка ≈ P/traf
Loss ≈ чистый потенциал по объёму спроса. Это не отменяет существующую
формулу «Балл = Частотность × вес интента × вес соответствия» (см.
«Интегральный балл SEO-приоритета» ниже) — P/traf-оценка **заменяет саму
Частотность** как более честное число (трафик, не сырой объём запросов), веса
интента/соответствия применяются к ней так же, как раньше. Когда появится
реальная органика (Yandex.Webmaster/Search Console на disrupt-hub.ru
покажут позиции), заменить константу 0.13 на настоящую CTR-кривую по
фактическим позициям и вычитать реальный текущий трафик — тогда P/traf Loss
станет содержательно отличаться от голой частотности, а не быть ей
пропорциональным.

### Двухступенчатый гейт: тема → ТЗ → черновик

Раньше был один гейт («тема утверждена Арсением» → дальше ТЗ и черновик
идут одним проходом, для routine — вообще без материализации ТЗ файлом).
Арсений явно попросил возможность открыть и посмотреть ТЗ **до того, как
статья уйдёт в написание** — это не косметика админки, это второй гейт в
процессе:

```
идея → [Гейт 1: тема утверждена] → ТЗ материализуется → [Гейт 2: ТЗ
утверждено] → черновик (Stage 3) → QC (Stage 4) → публикация (Stage 5)
```

И `hub-writer` (интерактивно), и облачная routine теперь обязаны:
1. Для утверждённой темы без ТЗ — написать ТЗ по расширенной структуре
   (см. Stage 2 ниже) и сохранить его, **не переходя к черновику в этом же
   проходе**.
2. Для темы, у которой ТЗ уже есть и имеет статус `approved`, — писать
   черновик по этому ТЗ.
3. Для темы, у которой ТЗ есть, но статус `draft` (ждёт решения Арсения) —
   пропустить: не дописывать ТЗ повторно, не начинать черновик.

**Осознанный побочный эффект для routine**: тема, которая раньше могла дойти
до `qc` за один прогон (пример — первая живая статья 2026-09-13), теперь
проходит минимум два прогона (написать ТЗ → дождаться утверждения → написать
черновик), то есть минимум один интервал расписания (6 часов) между ТЗ и
черновиком. Это согласуется с уже действующим принципом «Тёмп ограничен
проверкой, не генерацией» (см. «Жёсткие правила») — гейт добавляет реальную
человеческую проверку туда, где раньше её не было вообще (Stage 2 у routine
существовал только «в уме», не оставляя Арсению возможности его увидеть).

Хранение ТЗ и обе кнопки одобрения — см. «Дашборд «ТЗ»» в разделе «Админка и
SEO-инфраструктура» ниже.

| < 1 000 | 11.6% |
| 1 000–5 000 | 18.6% |
| **5 000–20 000** | **25.6% — самая большая доля** |
| 20 000–100 000 | 21.7% |
| ≥ 100 000 | 22.5% |

**Медиана — 14 068.** Полоса 5 000–20 000 — не единственная, но самая частая
одиночная полоса, и медиана падает прямо в её середину. Это и есть эмпирический
источник константы 0.13 в P/traf-оценке (см. выше) и число, вокруг которого
выстроена «целевая зона» ниже.

На уровне отдельной сырой фразы (лист «Семантика», 8 368 строк) картина другая:
68.4% фраз — меньше 1 000. Это ожидаемо и не противоречит выводу выше — ядро
всегда состоит из тысяч длиннохвостых фраз, из которых **группами** собирается
одна страница. Агентство не подбирает страницу под одну фразу и не смотрит на
топ отдельной фразы — оно смотрит на объём **группы**, ради которой и строится
страница. Ошибка хаба была именно в подмене уровня: сравнивали как «страница
под одну придуманную формулировку», а не «страница под группу реального
спроса».

### Почему именно эта полоса — логика, а не порог с потолка

**Почему не сверхширокая голова (>50 000–100 000+).** Разбор конкретных
примеров из файла показал два разных случая внутри «широкой головы»:

- Общеразговорные evergreen-темы вне ИИ-конкуренции («1 закон ньютона» —
  278 111, «что приготовить на ужин» — 912 686, «генератор случайных чисел» —
  1 309 074) — здесь P/traf MAX составляет только 3–16% от WS: даже позиция
  №1 не отбирает весь объём, потому что выдача перегружена конкурентами,
  featured snippets и смежными интентами. giga.chat может себе позволить
  побороться за такую страницу, потому что у домена уже есть трафик,
  доверие и десятки тысяч проиндексированных страниц — доменный авторитет,
  а не качество конкретной статьи, решает исход.
- У disrupt-hub.ru **нет** ни одного из этих преимуществ (новый домен, ноль
  истории индексации, ноль обратных ссылок) — конкурировать за головы такого
  масштаба с Хабром/Skillbox/Яндекс.Практикумом по темам вроде «нейросеть»
  в одиночку нереалистично на старте. Единственное исключение уже
  зафиксировано «Жёсткими правилами»: реальный продуктовый артефакт может
  оправдать заход на широкую тему, если статья выигрывает не позицией
  домена, а глубиной/уникальностью показанного сценария — но это
  осознанное исключение, не стратегия по умолчанию.

**Почему не сверхузкий хвост (<1 000–2 000).** Абсолютный объём трафика на
такую фразу физически мал — даже позиция №1 не окупает стоимость
производства статьи с реальным артефактом, QC и синдикацией. Полоса нужна
только как **сырьё для группировки** (несколько хвостовых фраз одного
интента складываются в один кластер ТЗ, см. Stage 2), не как самостоятельная
цель темы.

**Почему именно 5 000–20 000.** Это зона, где одновременно верны два условия:
фраза достаточно специфична, чтобы иметь один ясный интент (одна страница
способна закрыть её целиком, в отличие от головы, где под одним словом
скрываются разные задачи пользователя) — и достаточно объёмна, чтобы окупить
продакшн. У giga.chat в этой полосе соотношение P/traf MAX / WS заметно выше,
чем у сверхширокой головы (например «бритва оккама» 15 938 → P/traf MAX
3 612, то есть 22.7% — против 3–16% у мега-голов) — специфичный интент
конвертит в клик заметно охотнее.

### Наша фактическая картина на 2026-09-18 (диагноз, не повод для паники)

Прогон `admin/scripts/build-semantic-map.py` по всем 90 темам хаба:

- **Медиана частотности по всему бэклогу — 19.** 86.6% тем (58 из 67 с
  собранным числом) — ниже 1 000. Только 4 темы ≥ 5 000
  (`radar-5` — уже задокументированный false positive по неспецифичной
  фразе; `tool-1`, `concierge-7`, `korche-7`).
- Причина видна по самим формулировкам: подавляющее большинство тем —
  переформулированные блог-заголовки конкретных фич продукта («Установка
  Memento на macOS: с чего начать запись первой встречи» — 1;
  «Как получить от нейросети выводы по таблице с цифрами» — 21), а не
  сгруппированный реальный спрос. Это тот самый порядок «тема придумана
  → потом с трудом подобрано хоть какое-то число», который уже был
  диагностирован 2026-09-17 и исправлен только для тестовой партии
  Мультитула (Stage 1, «Семантика вперёд тем» выше) — остальные восемь
  продуктов остаются input-debt, как и было прямо зафиксировано тогда.
- Это не повод переписывать все 90 тем разом (см. «Существующие бэклоги...
  задним числом не переделываются» в Stage 1) — это повод **видеть** масштаб
  проблемы и иметь инструмент для целевого исправления при следующем
  плановом расширении бэклога каждого продукта.

### Дашборд «Семантическая карта»

Пятая вкладка админки (`tab-semantic`) — не создаёт тем и не пишет в бакет,
только визуализирует уже собранные данные (никаких новых запросов к
Wordstat). Источник — `admin/web/data/semantic-map.json`, строится
`admin/scripts/build-semantic-map.py` (тот же принцип «не трогать Cloud
Function», что у `topics.json`/`topic-frequency-details.json`: читает уже
существующие файлы, раскладывает по полосам, пишет статику).

На вкладке — сверху сравнение долей полос (giga.chat vs хаб, наглядно
показывает разрыв выше), затем по каждому продукту:
- **Темы бэклога по объёму спроса** — все темы продукта, отсортированные по
  частотности, с цветной полосой по банду (серый — длинный хвост, синий —
  узкая, зелёный — целевая зона, оранжевый — широкая голова).
- **Зоны роста** — фразы из уже собранного `similar[]` (топ-10 похожих
  запросов на голову каждой темы, снимается `apply-topic-frequency.py`),
  которые имеют приличный объём (не длинный хвост), но пока не являются
  анкором ни одной темы этого продукта. Это буквально данные, которые уже
  лежали в `topic-frequency-details.json` и нигде не были видны — например,
  для Мультитула тема `tool-1` подтягивает «нейросеть для презентаций
  бесплатно» (17 192) и «презентация с помощью нейросети» (12 100) как
  несформулированные темы.
- **Не проверено вручную** — среди зон роста будет бренд-шум конкурентов
  (тот же кейс Gamma, что уже пришлось исключать из tool-1 вручную, — здесь
  он снова всплывёт как «зона роста» с самым большим числом). Инструмент
  не пытается фильтровать бренды автоматически — решение остаётся за
  человеком, тот же принцип, что уже действует для `associations` в модалке
  частотности реестра тем.

### «Подтверждено рекламой» — синтез с реальными данными Директа (2026-09-18, вечер)

Арсений прямо указал: анализ полос Wordstat — это диагноз, а не решение;
«найти середину» означает не только целиться в полосу 5 000–20 000, но и
в первую очередь опираться на семантику, где Дизрапт **уже** хорошо
показывается и получает конверсии в живой рекламе — это сильнее любой
оценки по Wordstat, потому что это не потенциал, а состоявшийся спрос
именно нашей аудитории, а не абстрактного рынка.

**Источник** — `reports/15.09/Disrupt-15-09.xlsx` (Яндекс.Директ, данные по
13.09), листы `<Продукт> Ключи`: реальные показы/клики/CTR/конверсии/CR/CPA
по рекламным группам. Подключены Мультитул, Тайп, Айва — у них есть
конверсии на уровне ключей. Консьерж и Ника не подключены: у Консьержа
сумма конверсий по всему листу равна 0 на эту дату (нет усвояемого сигнала
на уровне ключей, а не ошибка чтения — проверено суммированием по всему
листу независимо от направления чтения колонок), у Ники нет продукта в
хабе (приостановлена).

**Найденная и исправленная ошибка при разборе (важно как прецедент).**
Первое чтение листа «Айва Ключи» «в лоб» по заголовкам колонок дало
абсурдные числа — 0.9 «кликов» на миллион показов, дробные «конверсии»
(23.81, 13.33). Причина — колонки `Клики`/`CTR,%` и `Конверсии`/`CR,%`
физически переставлены местами относительно заголовков именно на этом
листе (у «Мультитул Ключи»/«Тайп Ключи»/«Ника Ключи» — нет, там колонки
верны). Проверено самосогласованностью: `CPC × клики` должно давать расход,
`CPA × конверсии` — тоже; при обратном порядке колонок сходится ровно, при
прямом — нет, ни на одной строке. Второй найденный нюанс: кампания
`network_kw` Айвы (360 строк, самая крупная по показам) вообще не имеет
строк-итогов по группе — есть только построчная разбивка по фразам,
поэтому для комбинаций (кампания, группа) без отдельной итоговой строки
скрипт суммирует построчно, а не берёт готовый итог (иначе крупнейшие
показатели Айвы были бы полностью пропущены). Оба нюанса — ровно то, зачем
Арсений просил «перепроверить логику несколько раз», а не доверять сырому
чтению таблицы.

**Что показывает секция «Подтверждено рекламой» по каждому продукту**:
рекламные группы, отсортированные по числу реальных конверсий, с пометкой:
- **Нет темы в SEO** (зелёный) — реальная конверсия есть, статьи под неё
  нет. Прямой кандидат в бэклог, сильнее любой Wordstat-оценки. Пример:
  «улучшить текст» у Мультитула — 3036 конверсий, CR 19.72%, самая
  конвертящая группа во всём отчёте, но ни одна из 10 тем `tool-*` не
  целится в улучшение/исправление готового текста (все — про сборку
  презентаций, таблиц, документов, отчётов) — прямая рекомендация: тема
  под «нейросеть исправит текст/уберёт ошибки» должна встать в очередь на
  ТЗ одной из первых.
- **Есть тема в SEO** (синий) — сверка пройдена, конверсионный сигнал
  подтверждает уже выбранное направление.
- **Бренд конкурента** (серый, определяется по заглавной первой букве
  названия группы — в данных это надёжный маркер: у Айвы все бренд-группы
  — Clover/Clue/Flo/Yazio/MyFitnessPal/Lifesum/Clatch, остальные группы
  Мультитула/Тайпа/Айвы полностью строчные) — целевая реклама на чужой
  бренд, не тема для контента, аналогично уже известному кейсу Gamma у
  `tool-1`.

**Сопоставление «покрыто SEO» — не точное совпадение фразы, эвристика по
словам, дважды перепроверена и поправлена вручную.** Первая версия считала
темой покрытой при совпадении ХОТЯ БЫ одного значимого слова — это дало
ложное срабатывание: «улучшить текст» (топ-конверсия Мультитула) засчиталась
покрытой темой `tool-2` («превратить готовый текст в презентацию») только по
общему слову «текст», хотя задачи разные (исправить текст ≠ собрать из него
презентацию). Исправлено: если у рекламной группы больше одного значимого
слова, совпадения одного недостаточно — нужно минимум два; однословные
группы («документ», «презентация», «диктовка») по-прежнему покрыты при
совпадении своего единственного слова.

Второй проход той же вечерней проверки нашёл обратную ошибку — недосчёт, не
переучёт: точное сравнение строк не видело «цикл» и «цикла» как одно и то же
слово (разные падежные формы — разные строки), из-за чего «отследить цикл»
(топ-2 конверсий Айвы, 959) не совпадало ни с одной темой про цикл, хотя
`aiwa-9`/`aiwa-10` буквально про это. Добавлена грубая нормализация окончаний
(обрезка слов длиннее 4 символов до первых 4 — не настоящая лемматизация, но
покрывает большинство падежных форм) — после неё «отследить цикл» и «голос в
текст с ии» (у Тайпа) корректно стали `covered: true`: у `type-5` headPhrase
буквально «голосовой ввод текста офлайн» — тот же смысл, что у ad-группы,
просто в другой словоформе. **Остаточная неточность, которую эвристика не
решает и не должна:** совпадение идёт по headPhrase темы (фразе, по которой
снималась частотность), а не по факту, действительно ли заголовок
опубликованной статьи нацелен на этот же общий термин — `type-5` формально
покрывает «голос в текст», но заголовок статьи сужен до диктовки для юриста
и вряд ли будет ранжироваться по общему запросу. Флаг `coveredBySeo` — это
подсказка для быстрой сверки, не автоматический вердикт; окончательное
решение (нужна ли отдельная тема под голову «голос в текст» вместо/в
дополнение к узким сценариям) — за Арсением, тот же принцип, что уже
действует для «зон роста» и брендового шума.

**Вывод к предыдущему разбору.** Итоговая логика «найти середину» —
не одна формула объёма, а порядок проверки: сначала — какая семантика уже
доказала конверсию в рекламе (сильнейший сигнал, есть у Мультитула/Тайпа/
Айвы), и только для продуктов/тем без рекламных данных — полоса Wordstat
5 000–20 000 как ориентир при отборе.

Перегенерировать после каждого `apply-topic-frequency.py` (новые темы/
фразы) или обновления рекламного отчёта: `python3
admin/scripts/build-semantic-map.py` → задеплоить админку.

### Дашборд «Дерево семантики» (2026-09-19)

Отдельный раздел вкладки «Семантическая карта», под «Подтверждено
рекламой» — визуализация Stage 1, шагов 2-4 (см. «1. Бэклог тем» выше):
куда бурили и где вычерпано. Не пересекается по данным с «Темами бэклога»/
«Зонами роста» ниже (те строятся из уже собранного плоского `similar[]` в
`topic-frequency-details.json`) — дерево строится отдельным инструментом,
специально под многоуровневое бурение.

**Источник** — `admin/web/data/semantic-tree.json`, строит и дополняет
`admin/scripts/drill-semantic-tree.py <product> "<головная фраза>"`
(например: `python3 admin/scripts/drill-semantic-tree.py tool "презентация
нейросеть" --scenario "презентация"`). Политика дробления — та же, что в
Stage 1: топ-5 похожих фраз на узел, бурим дальше только те, что ≥ 3000, не
кладём в дерево вообще то, что ниже 500 (порог 2026-09-18), практический
потолок глубины — 3 уровня. Повторный запуск с тем же корнем не
переспрашивает уже собранные узлы (общий кэш с `wordstat-check.py`), можно
позвать с `--max-depth` побольше, чтобы продолжить бурить конкретное дерево
глубже. Правило на 403/429 — то же, что в `apply-topic-frequency.py`:
остановить весь прогон немедленно, без ретраев, сохранить собранное.

**Что видно на дашборде** — для каждого дерева: корень, сценарий, и вложенный
список узлов с отступом по глубине, у каждого узла — **два независимых
статуса**, не один (см. историю правки ниже, почему их два):
- **статус бурения** — «Пробурено» (узел пробурен дальше, у него есть
  собственные дети из его собственного `topRequests`) или «Бурить дальше»
  (узел ещё не спрашивали у Wordstat напрямую — только видели его в чужом
  списке похожих);
- **статус содержания** — «Есть статья» (фраза уже стала темой), «Нет
  потенциала» (известный бренд-шум конкурента), «Узко» (объём ниже целевой
  полосы 5000), «Есть потенциал» (всё остальное) — не зависит от статуса
  бурения: у пробуренного узла может быть «Есть потенциал», у ещё не
  пробуренного — «Нет потенциала», это два разных вопроса;
- **число** — широкая частотность (то же значение, что использовалось бы
  как «Частотность фразы» в реестре тем);
- **источник** — голова / похожая (`results`) / смежная (`associations`);
- **→ topicId**, если нормализованная фраза узла точно совпадает с
  `headPhrase` уже существующей темы — видно, куда конкретно из дерева
  выросла реальная тема, а не только что дерево существует само по себе;
- **заметка** — текст решения шага 5 («выбрана, потому что...»), если он
  уже вписан. Дашборд его только показывает, не редактирует.

**Заметки шага 5 — правятся вручную в `semantic-tree.json`, поле `note` у
узла**, тем же приёмом, что `topic-product-fit.json`: осознанно нет формы
для этого в админке — решение о хуке должно быть написано человеком как
рассуждение, а не выбрано из выпадающего списка. Заводить UI-редактор для
этого поля — значит превратить творческий гейт в чекбокс, то есть повторить
именно ту ошибку, которую всё это бурение должно исправить.

Живой пример на 2026-09-19 (Мультитул, корень «презентация нейросеть», 60
узлов, глубина до 3): второй проход вглубь на ветку «нейросеть для
презентаций бесплатно» (17 981) раскрыл «...на русском языке» (1 980),
«...без регистрации» (612), и associations на глубине 0 показали
неожиданную соседнюю категорию — «бесплатная нейросеть для генерации
изображений» (20 883) — тема для отдельного разбора (Мультитул умеет
генерировать изображения? — не выдумывать, проверить по PRODUCT.md перед
тем, как заводить тему).

## Процесс: восемь стадий

Статус темы движется последовательно. Файлы — в подпапках этой директории.

### 0. Бриф продукта для хаба
`briefing/<slug>-hub-briefing.md`. Что важно раскрывать, что нет — по
аналогии с тем разговором, который в своём процессе первым шагом ставит и
агентство. Разово на продукт, обновляется при крупных изменениях продукта.
Источник фактов — **`../DISRUPT.md`** (продуктовая база знаний: УТП, реальная

+ `../products/<slug>/PRODUCT.md`, без выдумывания.

### 1. Бэклог тем
`topics/<slug>-backlog.md`. **Порядок изменён 2026-09-17** (семантика
собирается до темы, не после) и **углублён 2026-09-19** (сборка семантики —
дерево вглубь + отдельный творческий шаг, не один срез + сортировка по
числу).

**Диагноз 2026-09-19, поставленный Арсением.** Сборка семантики — процесс
творческий, а не механический, а Stage 1 в прежнем виде вёл себя «как
компьютер»: один запрос → 10 похожих фраз → сразу выбор темы по объёму.
Между «широкой головой» и финальной темой должно быть 2-3 прохода
дробления, а не один, и должен быть отдельный шаг, где решение принимает не
формула, а суждение о том, какая ветка лучше показывает продукт. Живая
проверка на реальных данных (ветка `нейросеть для презентаций бесплатно`,
17 981, уже известная как «зона роста» для tool-1) подтвердила: второй
проход вглубь раскрыл то, чего не было видно на первом — «...на русском
языке» (1 980), «...без регистрации» (612), «...онлайн бесплатно» (876), и
соседнюю категорию спроса в associations — «бесплатная нейросеть для
генерации изображений» (20 883). Ни одна из этих формулировок не была бы
найдена, если бы Stage 1 останавливался на первом срезе.

**Шаг 1. Голова, не сценарий.** Точка входа — по-прежнему широкая головная
фраза сценария продукта (см. `briefing/<slug>-hub-briefing.md`), но она
воспринимается как **корень дерева**, а не как финальный запрос для
анализа. Дисциплина по формулировке головы не изменилась (лессон
2026-09-17): короткая головная фраза (1-2 слова + категория, например
«таблица нейросеть»), не придуманная длинная комбинация — Wordstat считает
широкое соответствие, и длинная выдуманная фраза превращается в новый узкий
запрос сам по себе, а не в точную версию головного (пример из практики:
«таблица нейросеть» → 5417, придуманная «таблица с формулами нейросетью» →
11 на той же теме).

**Шаг 2. Первый срез.** Один `topRequests` на голову через
`../shared/wordstat-check.py` — как раньше. Результат — `results` (похожие
фразы) и `associations` (смежные, шумнее). Отфильтровать явный шум (бренды
конкурентов, общее слово не по смыслу — см. пример «калории по фото» →
«бпла фото» в «Семантический срез перед ТЗ» ниже).

**Шаг 3. Второй срез — новое.** Для 3-5 самых объёмных живых веток из шага
2 (не для всех десяти — квота не бесконечна) повторить `topRequests` **на
саму эту ветку**. Это и раскрывает узкие, конкретные, эмоционально
заряженные хвосты уровня «на русском», «без регистрации» — то, что первый
срез физически не может показать, потому что это чужой топ-10, а не топ-10
дочерней фразы.

**Шаг 4. Углубляться, пока ветка продуктивна.** Не жёсткий лимит «ровно два
уровня» — если на глубине 2 ветка ещё раскрывается на новое и осмысленное
(не перефразировки уже увиденного, не шум), а объём не провалился ниже 500
— идти на глубину 3. Практический потолок — глубина 3 и не более 5 детей на
узел: дальше квота Wordstat не оправдывает разницу, а различимость
формулировок падает. Останавливаться на explicit-условии, не на интуиции:
объём ниже 500 (см. «Жёсткие правила», порог утверждён 2026-09-18) или
новые фразы дублируют уже увиденное по смыслу.

**Шаг 5. Творческий гейт — отдельно от объёма, без формулы.** Здесь
намеренно нет скоринга — балл в этом месте воспроизвёл бы ту же
«чопорность», от которой уходим. По каждой ветке, прошедшей фильтр объёма,
задаётся один вопрос вручную: **какую конкретную сильную сторону продукта
эта формулировка запроса приглашает показать?** Источник сильных сторон —
`PRODUCT.md`/`DISRUPT.md` (не выдумывать). Пример из проверки 2026-09-19:
«...на русском языке» приглашает показать нативную русскоязычность
интерфейса; «...без регистрации» — что Мультитул не требует подписки/
аккаунта. Ветка без продуктового приглашения (гипотетически — узкая тема не
про инструмент, а про постороннее содержание) не идёт в очередь, даже при
хорошем объёме. **Решение фиксируется текстом** («тема выбрана, потому
что...») в карточке дерева (см. «Дашборд «Дерево семантики»» ниже) — не
чекбоксом и не баллом, ровно по той же причине, по которой P/traf-оценка не
заменяет человека при утверждении темы.

**Шаг 6. Только теперь — формулировка темы.** Тема собирается из победившей
ветки шага 5 + продуктового отличия, которое она приглашает показать, не
из сценария продукта, придуманного заранее. Частотность заполняется в
бэклог сразу из уже снятого числа, не оставляется `[TBD]`.

**P/traf-оценка (частотность × 0.13, см. выше) и целевая полоса 5 000–20 000**
остаются ориентирами на шаге 6 — они сортируют кандидатов и подсказывают
глубину, на которой скорее всего лежит хороший баланс объёма и
специфичности, но не решают вместо шага 5. Полный логический разбор полосы
— «Семантическая карта: полосы объёма спроса» ниже.

**Инструмент.** Дерево строится и хранится через
`admin/scripts/drill-semantic-tree.py` (пишет `admin/web/data/
semantic-tree.json`), видно во вкладке «Семантическая карта» — раздел
«Дерево семантики»: два независимых статуса на узел — куда ещё стоит
бурить (пробурено / бурить дальше) и что из уже собранного годится в
статью (есть потенциал / нет потенциала / узко / уже есть статья). См.
«Дашборд «Дерево семантики»» в разделе «Админка и SEO-инфраструктура»
ниже.

Существующие бэклоги (`tool` и остальные девять) заведены до решения
2026-09-17 методом чистого брейнсторма — **задним числом не
переделываются**, это входной долг, а не нарушение: пересматривать их
семантику по новому порядку (включая дерево) при следующем плановом
расширении бэклога каждого продукта, не разово ради формальности. Новые
темы и новые продукты — только по новому порядку.

**Гейт 1: темы утверждает Арсений** до перехода на ТЗ.

### 2. ТЗ / бриф статьи
**Обязательная материализация файлом с 2026-09-17 — для `hub-writer` И для
routine одинаково** (раньше у routine это существовало только «в уме»,
файла не было никогда, `briefs/` пуст по сей день). Без файла нет второго
гейта — Арсению нечего смотреть перед тем, как статья уйдёт в написание.

Локально: `briefs/<slug>/<topic-slug>-<YYYY-MM-DD>.md`, фронтматтер
`{topicId, product, status: draft|approved, createdAt}`. Публикуется в бакет
`disrupt-hub-content` тем же способом, каким публикуются статьи (Stage 5),
только под префиксом `_briefs/` — `_briefs/<product>/<topicId>.md`, тот же
приём, что уже используют оверрайды статуса тем (`_topics/`, см. «Одобрение
темы прямо из дашборда»): валидация Cloud Function требует только
`key.endsWith(".md")`, ни строчки правки на бэкенде. Путь 1 (локально) —
`node admin/scripts/publish-brief.mjs <файл>`; путь 2 (routine) — прямой
`PUT` на тот же invoke URL, как и для статей.

**Структура ТЗ (расширена 2026-09-17 по образцу реальных ТЗ giga.chat)**:

- **Предлагаемая страница** — `/<product>/<slug>/`, новая или под рерайт
- **Формат** — лонгрид или «живой пример» (см. «Стилистика и подбор тем
  giga.chat» выше — короткая форма не снижает требование к артефакту,
  просто уместнее для узкого сценария)
- **H1** (короткий вопрос читателя) + **metaTitle** (H1 + уточнение, не
  дубль, 40–60 символов) + **metaDescription** (150–160 символов, выгода, не
  список ключей) — лимиты и обоснование в «Стандарт письма» выше
- **Кластер интентов** — конкретные фразы из Stage 1 (не одно ключевое
  слово), с частотностью каждой
- **Конкурентная выдача** — 3–5 реально существующих публикаций по головной
  фразе кластера (WebSearch), с пометкой, что именно они раскрывают —
  калибровка глубины покрытия, не референс для копирования
- **Таблица ключевых фраз** — фраза / минимум органичных упоминаний /
  **потолок «не более 1 вхождения на 300 знаков»** (перенесено из ТЗ
  giga.chat буквально — это ограничение сверху против переспама, согласуется
  с уже действующим «плотность не метрика» из «Стандарт письма», не вводит
  вторую метрику)
- **LSI и смежные фразы** — по возможности, из `results`/`associations`
  того же Wordstat-запроса
- **Аутлайн** H2/H3 с указанием, какой реальный экран/настройка/промпт нужен
  в каждом блоке и в каком предложении интро упоминается продукт со ссылкой
- **Перелинковка** — на лендинг продукта (в интро) + 5–10 ссылок на другие
  статьи хаба, разный анкор
- **Источники фактов** — конкретные разделы PRODUCT.md/PRODUCTS.md, без
  выдумывания

Объём текста не задаётся заранее — решает глубина покрытия кластера, не
таргет слов (правило не изменилось).

### 3. Черновик статьи
`articles/<slug>/<topic-slug>.md`. E2E-статья по ТЗ.

**Конвенция иллюстраций (расширена 2026-09-13).** На каждое место в статье,
которому нужен визуал, — один из двух маркеров, решение за агентом по
принципу «это реальный артефакт продукта или декоративная/пояснительная
картинка»:

- **`[SCREENSHOT: <подробный бриф для человека>]`** — когда нужен настоящий
  экран продукта (это и есть жёсткое правило «без реального артефакта — не
  публикуем», отменить нельзя никаким промптом). Бриф — не одна строка, а
  инструкция, по которой Арсений сможет снять экран не думая: что именно
  открыть, какой ввести запрос/настройку, что должно быть видно в кадре,
  какая тема оформления, что заведомо НЕ должно попасть в кадр (чужие данные,
  реальные ФИО и т.п.). Формат: `[SCREENSHOT: шаги 1) ... 2) ... 3) ...;
  видно в кадре: ...; тема: light/dark; не показывать: ...]`.
- **`[AI-IMAGE: <промпт для генерации>]`** — только для декоративных или
  объясняющих изображений, которые НЕ выдают себя за интерфейс продукта
  (обложка, схема, иконка-метафора). Никогда не заменяет `[SCREENSHOT: ...]`
  там, где смысл абзаца — «вот как это выглядит в продукте». Промпт — сразу
  готовый к вставке в генератор (стиль, композиция, без текста на картинке,
  без брендинга Сбера — независимый брендинг).

Оба маркера — не выдумка контента, а поручение: агент никогда не описывает
внутри статьи то, чего не видел (никаких «на скриншоте видно, что...» до
того, как скриншот появится).

`[SETTING: описание]` — для описания конкретной настройки продукта текстом
(не изображение), используется как раньше.

### 4. QC — три чек-пойнта
1. Соответствие ТЗ (кластер покрыт — отобранные в Stage 2 фразы органично
   встречены в тексте, H1/meta на месте и в лимитах символов, формат
   соблюдён, продукт упомянут со ссылкой в интро, термины при первом
   употреблении расшифрованы в скобках) **+ SEO-структура и анти-слоп** по
   чек-листу «Стандарт письма» выше (заголовки читаются как карта статьи,
   первый абзац без раскачки, ни канцелярита, ни диалоговых утечек модели,
   ни инфляции значимости — с поправкой на правило анти-сверхкоррекции)
2. Продуктовые факты и бренд-правила (независимый брендинг, запреты по
   продуктам — мед. заявления Айвы, этика звонка Консьержа, размежевание
   Ники и Консьержа по механике, а не по задаче)
3. Пост-паблиш техничка (мета/H1 живые на сайте, ссылки резолвятся) — после
   публикации dev-командой

Финальный ОК — **только Арсений**. Агент не самоапрувит.

### 5. Хэндофф на публикацию
**Изменено 2026-09-13, с появлением админки (см. «Админка и SEO-инфраструктура»
ниже).** Сайт больше не читает `articles/` напрямую — источник Astro-коллекции
теперь `articles-published/`, зеркало бакета `disrupt-hub-content`. Просто
поменять `status` в локальном файле `articles/<slug>/` больше не публикует
его — файл должен физически попасть в бакет. Статус после хэндоффа — **`qc`**,
не `published`: Финальный ОК остаётся только за Арсением (см. Stage 4), пуш в
бакет лишь делает черновик видимым и редактируемым в админке.

**Путь 1 — локально (Claude Code на машине Арсения):** запустить `node
disrupt/hub/admin/scripts/publish.mjs <путь-к-файлу>` — скрипт кладёт файл в
бакет через Cloud Function (с проверкой ETag, чтобы не перезаписать
параллельную правку из веб-админки). Секрет — в `admin/scripts/.env.local`
(untracked), агент его не видит и не должен искать.

**Путь 2 — облачный routine (автономный, без Claude Code на месте).** У
routine нет доступа к локальным файлам и `.env.local` — вместо `publish.mjs`
он делает прямой HTTP-запрос к той же Cloud Function: `PUT <invoke URL>`,
заголовок `X-Admin-Key: <ADMIN_SECRET>` (передан в промпте routine, не
хранится в git), тело `{"key": "<product>/<slug>.md", "raw": "<полный текст
файла с фронтматтером>"}` для статьи, `{"key":
"_briefs/<product>/<topicId>.md", "raw": "..."}` для ТЗ (см. Stage 2,
«Двухступенчатый гейт» выше). Перед тем как писать новую статью, routine
обязан проверить `GET <invoke URL>?action=list` с тем же заголовком и
посчитать, сколько статей сейчас в статусе `draft`/`qc` (ещё не
`published`) — если ≥ 3-5 (см. «Жёсткие правила», темп ограничен проверкой),
в этот прогон новых статей не добавлять. Это ограничение — про статьи;
написание ТЗ (Гейт 1→2) отдельным лимитом очереди не ограничено, см.
алгоритм в «Автономное написание статей» ниже.

### 7. Синдикация

**Расширено 2026-09-17 — ремесло хуков для ленты.** Оригинал на
disrupt-hub.ru живёт по правилам «Стандарт письма» (анти-слоп, заголовок
самодостаточен, без литературных красивостей) — это правила для **поиска**,
где статья конкурирует с запросом, и переспам хука бьёт по поведенческим
факторам (pogo-sticking). Синдикация конкурирует с **лентой** (Dzen/VC/Habr
показывают статью вперемешку с сотнями других, решение о клике — за
секунду) — это другая площадка с другими правилами кликабельности, и до
этой правки в HUB.md не было ремесла под неё, только тон.

**Правило: у синдицированного пакета свои заголовок и свой открывающий
абзац, отдельные от H1/интро оригинала.** Не копия с адаптированным тоном
поверх — самостоятельный вход в текст, дальше по телу — адаптация
(пересказ, не копипаста), в конце — ссылка на оригинал.

**Хуки, которые остаются внутри правил (используются и в оригинале, и здесь
усиленно):**
- Конкретное число вместо общей фразы (у нас уже есть частотность по
  Wordstat на каждую тему — использовать её как контекст: «Это ищут N раз в
  месяц»)
- Квантифицированное до/после («вместо вечера вручную — несколько минут»)
- Личный/инсайдерский заход от лица команды («мы сделали», «мы
  протестировали») — не обезличенный редакторский тон оригинала

**Хуки, которые остаются вне правил и здесь тоже** (не переносим): заголовки-
клиффхэнгеры без ответа в тексте, эмоциональные усилители и восклицания,
искусственная срочность/FOMO — это конфликтует с брендом продукта
независимо от площадки, разница между поиском и лентой этого не отменяет.

| Dzen | Число или контраст в заголовке; короткий связный абзац-затравка — Dzen показывает сниппет интро в ленте, от него зависит клик | Ближе к оригиналу, RU-нативная площадка | — |

**Структура пакета** — `syndication/<slug>/<platform>-<topic-slug>-<DATE>.md`
локально, фронтматтер `{topicId, product, platform, status: draft|ready|

## Жёсткие правила

- **Без реального артефакта продукта — не публикуем.** Ни одна статья не
  выходит только на общих советах: это ровно то, что Google квалифицирует
  как scaled content abuse.
- **Не выдумывать продуктовые факты.** Экраны, настройки, цифры — только из
  PRODUCT.md/PRODUCTS.md или реальной съёмки. Нет — плейсхолдер, не догадка.
- **Независимый брендинг.** Правила режима A (палитра GigaChat, SB Sans) к
  хабу не применяются, если только сайт не решит иначе на своей стороне —
  это не зона контентного движка.
- **Продуктовые запреты не отменяются потому, что это SEO-контент**: Айва —
  без диагнозов и гарантий результата, с дисклеймером «не заменяет
  консультацию врача»; Консьерж — без захода в этическую рамку звонка;
  Ника/Консьерж — сценарии разводятся по механике (онлайн-путь vs звонок),
  не по задаче, чтобы статьи не сталкивали продукты лбами в одной выдаче.
- **Синдикация не раньше индексации оригинала**, с лагом. Habr — только
  органичный голос команды.
- **Тёмп ограничен проверкой, не генерацией.** Дефолт — не больше 3–5
  черновиков в очереди на QC одновременно у Арсения; корректируется по факту
  реальной пропускной способности.
- **Числа — с источником.** Частотность, охват, конверсии — из выгрузки или
  Вордстата по конкретному запросу, иначе `[TBD]`.
- **Анти-слоп вычитка обязательна перед Stage 4.** Без неё статья не уходит
  на QC — правило анти-сверхкоррекции (см. «Стандарт письма» выше) не
  освобождает от вычитки, а задаёт её меру: чистить кластеры примет, не
  резать факты.
- **Длина не подгоняется под таргет слов.** Решает глубина покрытия кластера
  интентов, растягивание объёма ради вида «лонгрида» запрещено.
- **Черновик не начинается без утверждённого ТЗ.** Гейт 2 (см.
  «Двухступенчатый гейт» выше) — ни `hub-writer`, ни routine не пишут Stage 3
  по теме, чей `_briefs/<product>/<topicId>.md` ещё в статусе `draft`.
- **Семантика собирается до темы, не после.** Новые темы и новые продукты
  проходят точечный Wordstat-запрос по ведущему сценарию продукта раньше,
  чем формулировка темы попадает в бэклог (см. Stage 1, «Семантика вперёд
  тем» выше) — существующие бэклоги, заведённые до 2026-09-17, входной долг,
  не пример для новых.
- **Минимум 500 запросов на тему, без исключений** (добавлено 2026-09-18,
  прямое указание Арсения). Тема с измеренной частотностью ниже 500 не
  показывается в «Реестре тем» вообще — не фильтр, который можно снять, а
  жёсткая отсечка: трафика физически нет, писать статью под такой спрос —
  тратить продакшн впустую. Правило применяется к уже измеренным темам
  (`freqNum < 500`); темы без данных (`[TBD]`) не дисквалифицированы, они
  просто ещё не проверены. Правило не распространяется на «Подтверждено
  рекламой» (см. «Семантическая карта» ниже) — там сигнал сильнее любой
  оценки объёма, это уже состоявшаяся конверсия, а не прогноз по фразе.
  «Семантическая карта» тоже не фильтруется этим порогом — она диагностический
  инструмент и обязана показывать полный масштаб проблемы (длинный хвост
  включительно), а не прятать его.

## Админка и SEO-инфраструктура (2026-09-13)

Арсений явно попросил веб-админку статей с редактором и SEO-чеклистом,
явно выбрал хостинг на собственном Yandex Cloud (не Claude Artifact — там
CSP блокирует произвольный fetch к внешним API), и явно попросил широкий
чеклист по образцу процесса SEO-команды giga.chat.

**Хранилище и разделение с рабочей папкой hub-writer.** Новый бакет
`disrupt-hub-content` — канонический источник статей (`.md` с тем же
фронтматтером). Новая директория `disrupt/hub/articles-published/` —
зеркало этого бакета, и только зеркало; `content.config.ts` теперь читает
её, а не `articles/`. `articles/` (рабочая папка `hub-writer` для
idea/brief/draft/qc) не тронута специально: `npm run sync-content`
использует `aws s3 sync --delete`, и если бы он синхронизировал `articles/`
напрямую, любой локальный черновик, который ещё не попал в бакет, был бы
удалён при первом же деплое, случившемся во время работы `hub-writer`. Два
каталога = два владельца, ноль пересечения по умолчанию.

**Cloud Function публичная, не приватная.** Первая идея — приватная функция
+ API-ключ — не работает: браузерный CORS-preflight (`OPTIONS`) никогда не
несёт кастомный `Authorization`, а Yandex режет приватную функцию без него
ещё на уровне платформы, до кода. Функция публичная
(`allow-unauthenticated-invoke`), `OPTIONS` отвечает `204` без проверки,
`GET/PUT/DELETE` сверяют заголовок `X-Admin-Key` с `ADMIN_SECRET` в коде —
тот же по силе bearer-secret, что и API-ключ, без второго сервис-аккаунта и
без проблемы preflight. Доступ к бакету — статический access key отдельного
сервис-аккаунта `disrupt-hub-content-sa` (роль `storage.editor`, только этот
бакет) в переменных окружения функции. Код — `disrupt/hub/admin/function/`.

**Публикация ≠ деплой сайта.** Сохранение/публикация в админке (или через
`publish.mjs`) кладёт файл в `disrupt-hub-content` — не пересобирает и не
выкатывает сайт. `npm run deploy` (теперь `sync-content && astro build && aws
s3 sync ...`) остаётся ручным шагом «выкатить в прод», как и раньше.

**SEO-поля — что реально добавлено в схему, а что нет.** Тест: есть ли в
этой же задаче реальный потребитель поля. `canonical` (переопределение,
по умолчанию считается из пути файла), `ogImage`, `robots`, `schemaType`
(`Article`/`HowTo`) — да, `BaseLayout.astro`/`[slug].astro` их рендерят →
добавлены в Zod-схему `content.config.ts`. «Широкие» giga.chat-поля
процесса (дедлайн, копирайтер, редполитика) — **сознательно не добавлены**:
живого потребителя нет (один автор — `hub-writer`, ни календаря, ни второй
роли), а это ровно тот же принцип «не заводить поле под процесс, которого
ещё нет», который уже был записан в этом файле раньше — не повторяем его же
нарушение в схеме. «Широкое» ревью реализовано иначе: в самой админке есть
три сессионных чекбокса (ТЗ в `briefs/`, бренд-правила, 3 QC-чекпойнта),
которые блокируют выбор статуса `published`, пока не отмечены — ничего из
этого не пишется в файл, поэтому не может стать мёртвым грузом.

Заодно закрыты несколько пунктов `platform-technical-seo.md` в коде сайта:
`rel=canonical`, `meta robots`, Open Graph/Twitter, JSON-LD (Article/HowTo),
XML sitemap (`@astrojs/sitemap`), блок «похожие статьи» того же продукта на
странице статьи (перелинковка — источник называл её «без этого краулер
почти не доходит до статей»). Не закрыто: редиректы, Core Web Vitals —
вне фазы 1, см. `platform-technical-seo.md`.

**Вне фазы 1, явно:** загрузка изображений (плейсхолдеры `[SCREENSHOT: ...]`
остаются), rich-редактор (только textarea + markdown-превью), мультипользо-
вательские роли, история версий/откат, автодеплой сайта по факту публикации,
API Gateway/кастомный домен для функции, Lockbox для секретов (пока —
переменные окружения функции).

**Ручная настройка Yandex Cloud завершена и проверена 2026-09-13** (сервис-
аккаунт, статический ключ, функция, переменные окружения, `.env.local`) —
подробности и живые адреса в `site/README.md`, раздел «Админка». Обнаружено
и исправлено в процессе: (1) функция вернула бы 500 вместо 404 на запрос
несуществующей статьи — правило конфликтов `publish.mjs` на это опиралось;
(2) первая версия `publish.mjs` сверяла etag со свежим GET прямо перед
своим же PUT, из-за чего конфликт никогда не мог сработать — тихая
перезапись правки из веб-админки была обнаружена вручную и закрыта
локальным файлом состояния `.publish-state.json`; (3) автосоздание версии
функции по ссылке на объект в Object Storage дважды ломалось необъяснимо —
рабочий путь оказался только ручной загрузкой ZIP через консоль.

**Дашборд «Реестр тем» (добавлено 2026-09-13).** Арсений заметил, что
админка показывала только написанные статьи (2 шт.) и не давала увидеть
весь бэклог из 90 тем — сколько утверждено, сколько ещё «идея», по каким
продуктам вообще ничего не одобрено. Новая вкладка в админке
(`admin/web/index.html`, кнопка «Реестр тем») сводит `topics/*-backlog.md`
(источник статусов «идея»/«утверждено») со списком реальных статей из
Cloud Function (`?action=list`) в одну таблицу: сводка по продуктам (тем /
утверждено / написано / опубликовано), фильтры по продукту и статусу,
кнопка «Открыть →» на написанные, отдельный блок для статей без `topicId`
(«не привязано к бэклогу»).

Сознательное архитектурное решение — **не трогать Cloud Function**. Её
деплой — единственное по-настоящему хрупкое звено всей админки (см. выше:
только ручная загрузка ZIP через консоль, автосоздание версии по ссылке на
объект дважды ломалось необъяснимо). Вместо нового эндпоинта — статический
`admin/web/data/topics.json`, генерируемый локальным скриптом
`node admin/scripts/sync-topics.mjs` (парсит все `topics/*-backlog.md` по
именам колонок в заголовке таблицы, не по фиксированной позиции — у
`aiwa-backlog.md` на одну колонку больше остальных) и заливаемый вместе с
остальной статикой админки обычным `npm run deploy:admin` — ни единой
строчки в `admin/function/`. **После любой правки статусов в
`topics/*-backlog.md` дашборд не обновится сам** — нужно руками прогнать
`sync-topics.mjs` и передеплоить `admin/web/` тем же `deploy:admin`.

Связь «написанная статья ↔ строка бэклога» — новое обязательное поле
`topicId` во фронтматтере (см. пример фронтматтера выше). Задним числом
проставлено двум уже существовавшим статьям (`tool-1`, `tool-5`) прямым PUT
через Cloud Function. Промпт автономной routine (см. ниже) обновлён
2026-09-13 тем же днём: обязана проставлять `topicId` и сверять дубликаты
по нему, а не по тексту заголовка.

**Одобрение темы прямо из дашборда (добавлено 2026-09-13, тем же днём).**
Арсений попросил менять статус темы «идея → утверждено» прямо в реестре, а
не редактируя `topics/*-backlog.md` руками — чтобы облачная routine сразу
подхватила тему на следующий прогон. Источник правды для статуса темы
остаётся `topics/*-backlog.md` в git (оба места — локальная копия и
зеркало `arbort/disrupt-hub` — не переписываются кнопкой «Утвердить»), но
поверх него введён **живой слой оверрайдов**: кнопка кладёт в тот же бакет
`disrupt-hub-content` крошечный `.md`-объект `_topics/<topicId>.md` с
фронтматтером `{topicId, status}` — снова без единой правки Cloud Function,
объект просто проходит существующую валидацию PUT (`key.endsWith(".md")`).
`?action=list` неизбежно возвращает эти объекты вперемешку с настоящими
статьями — отфильтрованы из списка статей и «сирот» на клиенте по префиксу
`_topics/`, различить статью и оверрайд можно и по полям (у статьи есть
`title`, у оверрайда — только `topicId`+`status`).

Приоритет статуса темы в реестре: **написанная статья > живой оверрайд >
статус из git-файла**. Кнопка «Вернуть в идею» удаляет оверрайд (DELETE),
после чего тема просто показывает то, что написано в git-файле — если там
и так «утверждено», кнопки нет вообще (нечего откатывать через дашборд, это
меняется только в файле). Тема со статусом «идея — блокировано» кнопки
«Утвердить» не получает — блокировка продуктового/юридического вопроса не
должна сниматься одним кликом мимо разбора, который её туда поставил.

Промпт routine обновлён снова тем же днём: гейт «утверждено» теперь
выполняется по ИЛИ — git-файл ИЛИ живой оверрайд в бакете, дубликаты и лимит
очереди по-прежнему считаются только по настоящим статьям (объекты
`_topics/*.md` явно исключены из подсчёта). Живой оверрайд НЕ переносится
обратно в git-файл автоматически — при генеральной уборке бэклога стоит
сверить `_topics/*.md` в бакете с `topics/*-backlog.md` и снести те
оверрайды, для которых статья уже написана (дальше они не нужны, приоритет
"написанная статья" их и так перекрывает, но за место в бакете и лишний
`GetObject` в `?action=list` не платить смысла нет).

**Широкая частотность по 62+ из 90 тем (снята 2026-09-13, тем же днём).**
Арсений спросил про балльную SEO-систему приоритета тем. Реализовано без
отдельного «балла» — просто заполнена уже существовавшая колонка (в
реестре подписана **«Широкая частотность»**, не просто «Частотность» —
Арсений явно попросил переименовать, чтобы название не звучало точнее,
чем есть на самом деле: метод не умеет считать частоту по точной фразе,
только по широкому соответствию) реальными числами через Wordstat API.
Ручная работа: заголовки бэклога — блог-формулировки («Как собрать
презентацию для клиента без дизайнера»), а не то, что реально вбивают в
поиск, поэтому для каждой темы вручную подобрана короткая поисковая фраза
(файл `admin/scripts/topic-phrases.tsv`, без названий продуктов — по ним
пока нет спроса, интересен спрос на саму идею/сценарий). Скрипт
`admin/scripts/apply-topic-frequency.py` пишет число прямо в
`topics/*-backlog.md`, заменяя `[TBD]` — правится источник правды, не
отдельный слой; уже заполненные ячейки скрипт **не перезаписывает** —
это не только защита от лишних вызовов API, но и (см. ниже) защита от
собственной нестабильности метода.

**Известный false positive:** `radar-5` («вход без пароля») дал 234 015 —
фраза неспецифична продукту (логин вообще, любой сервис), число не
индикатор реального спроса на эту тему конкретно, читать с поправкой на
это при просмотре реестра.

**Правило на 403 и на часовую квоту (429), изменено 2026-09-13 по прямому
указанию Арсения — НЕ так, как в `wordstat-check.py`.** Там 403 считается
флейком (~1/6 запросов) и ретраится с бэкоффом — оправдано для короткого
ручного списка. Здесь батч большой (90 тем) и не срочный: при любом 403
или 429 скрипт останавливает **весь прогон немедленно**, без единого
повтора, печатает список недоснятых тем и завершает работу — «остальное
доснимем в следующий запуск», квоту не жжём и не спамим. Реализовано
отдельным однократным HTTP-вызовом в `apply-topic-frequency.py` (не через
retry-цикл класса `Wordstat` — оттуда переиспользованы только константы
эндпоинта/каталога/региона, не логика ретраев).

**Детальная карточка «из чего складывается частотность» (добавлено
2026-09-13).** Клик по названию любой темы в реестре открывает модальное
окно: использованная фраза, число как в реестре, список похожих
уточняющих запросов с их отдельными числами (`results` в ответе Wordstat
— это и есть «за счёт каких ключей она складывается»), отдельно смежные
ассоциации (`associations` — по наблюдению шумнее: могут быть вообще не
по теме, например у фразы «калории по фото» в associations всплывали
«бпла фото», «колизей фото» — общее слово «фото», не по смыслу). Данные —
`admin/web/data/topic-frequency-details.json`, генерируется тем же
`apply-topic-frequency.py` (снимает `numPhrases=10` вместо прежних 3).

**Найдена реальная нестабильность метода при сверке (не баг кода).** При
повторном снятии одной и той же фразы `totalCount` иногда меняется — из
12 сверенных фраз 3 дали другое число при повторном вызове (например
«трекер беременности»: 1648 → 98 при идентичной фразе, только другой
`numPhrases`). Это не ошибка сопоставления и не деградация показателя со
временем — похоже на нестабильность/семплирование на стороне API между
вызовами. Из-за этого модалка **не показывает `totalCount` из последнего
снятия как истину** — headline всегда берётся из реестра/backlog-файла
(число, которое уже зафиксировано и не трогается лишний раз), а если
последнее снятие разбивки дало другое число — модалка явно показывает
предупреждение с обоими числами, не молчит о расхождении.

Перегенерировать после правки фраз или дозаписи оставшихся тем:
`python3 admin/scripts/apply-topic-frequency.py` → `node
admin/scripts/sync-topics.mjs` → `npm run deploy:admin`. Скрипт
идемпотентен — при повторном запуске подхватывает недоснятое с прошлого
раза и не трогает уже заполненные ячейки backlog.

**Интегральный балл SEO-приоритета (добавлено 2026-09-13, тем же днём).**
Арсений явно попросил разложить оценку на видимые критерии, а не спрятать
её в один непрозрачный балл — по образцу того, как агентство giga.chat
обосновывает выбор тем ценностью трафика, и по общей практике SEO
(объём × интент × соответствие продукту, см. WebSearch-находки в ответе
сессии — не отдельно задокументированы файлом, только здесь). Формула:

```
Балл = Частотность (Wordstat) × вес интента × вес продуктового соответствия
```

- **Интент** выводится автоматически из уже существующей колонки «Кластер /
  интент» (простой substring-матчинг: «коммерческ» → commercial, «навигацион»
  → navigational, «брендов» → brand, иначе informational — не отдельный
  файл, значение всегда синхронно с бэклогом). Веса: коммерческое ×1.0,
  брендовое ×0.6, навигационное ×0.4, информационное ×0.35 — коммерческий
  интент ближе всего к целевому действию (установка продукта), у нас нет
  монетизации кликом, поэтому чисто информационный трафик ценится ниже.
- **Продуктовое соответствие** — ручная разметка «якорная / периферийная»,
  `admin/scripts/topic-product-fit.json` (60 anchor / 30 peripheral из 90).
  Якорная — тема демонстрирует один из ведущих сценариев продукта, названных
  в его `briefing/<slug>-hub-briefing.md` (например, у Мультитула это три
  сценария с лендинга — презентация/таблица/исследование; у Тайпа — почти
  все темы, кроме онбординга, потому что у продукта один сценарий на разные
  аудитории). Периферийная — второстепенная фича, онбординг/навигация,
  чистое сравнение или brand-кейс без демонстрации ведущего сценария. Веса:
  anchor ×1.0, peripheral ×0.6. Требует чтения briefing-файла человеком —
  не выводится автоматически, в отличие от интента.
- **Правило 70/20/10 по продуктам сюда не входит.** Это фильтр *очерёдности
  продвижения* (какой продукт продвигать активнее — см. «Приоритизация
  производства» выше), а не часть оценки конкретной темы: тема оценивается
  объективно вне зависимости от того, чей это продукт — сильная тема
  Disrupt Radar не может обогнать слабую тему Мультитула по очереди в
  производство, но её балл считается тем же способом, без скидки.

Все компоненты видны как отдельные колонки в реестре (Частотность / Интент
/ Соответствие / Балл) — заголовки кликабельны и сортируют таблицу по
убыванию/возрастанию. Добавлены фильтры по интенту и по соответствию.
**Финальное решение — за человеком**, балл не решает и не блокирует кнопку
«Утвердить». Показательный пример почему: `radar-5` (обсуждался выше как
false positive по фразе) даже после весов навигационное×0.4 и
периферийная×0.6 всё равно верхний по баллу (56 164) — сырой выброс частоты
слишком велик, чтобы веса его подавили. Балл — это прозрачная сортировка по
трём честным прокси, не автоматический вердикт.

Веса не откалиброваны по реальным данным (сайт ещё не публиковал статей,
истории конверсии нет) — это осознанные, объективные, но пока не проверенные
допущения. Пересмотреть, когда появится аналитика по опубликованным статьям.

**Частотность → P/traf-оценка (2026-09-17).** По методологии giga.chat (см.
«Семантика вперёд тем» выше) сырая широкая частотность заменена на
P/traf-оценку (частотность × 0.13) как вход в формулу «Балл» — то же место в
формуле, честнее число: это прикидка трафика, а не объём запросов. Колонка
в реестре подписана «P/traf-оценка», не «Частотность» — по тому же принципу,
по которому «Частотность» когда-то переименовали в «Широкую частотность»
(название не должно звучать точнее, чем метод).

## Дашборд «ТЗ» (добавлено 2026-09-17)

Третья вкладка админки, `admin/web/index.html` (`tab-briefs`) — закрывает
прямой запрос Арсения: увидеть и открыть ТЗ по конкретной теме **до того**,
как статья уйдёт в написание (Гейт 2, см. «Двухступенчатый гейт» выше).

Источник данных — те же объекты `_briefs/<product>/<topicId>.md` из общего
`?action=list` (никакой отдельной ручки, тот же принцип «не трогать Cloud
Function», что и у дашборда тем). Список ТЗ группируется по продукту и
статусу (`draft` — ждёт решения, `approved` — одобрено, ещё без статьи),
клик открывает полный текст ТЗ (рендер markdown тем же `marked.js`, что уже
используется в превью статьи). Карточка ТЗ показывает: H1/metaTitle/
metaDescription, кластер интентов с частотностью, конкурентов, таблицу
ключевых фраз, аутлайн — то есть весь Stage 2 целиком, не выжимку.

Две кнопки: **«Утвердить ТЗ»** (PUT того же объекта с `status: approved` —
на следующем прогоне routine возьмёт эту тему в черновик) и **«Вернуть на
доработку»** (обратно в `draft`, с местом для комментария в теле объекта —
routine его не читает, это заметка для `hub-writer`/самого Арсения при
следующей ручной правке). Строка реестра тем (вкладка «Реестр тем») получает
дополнительную ячейку — ссылку «ТЗ →», если для этого `topicId` существует
`_briefs/`-объект, независимо от его статуса.

Публикация ТЗ с локальной машины — `node admin/scripts/publish-brief.mjs
<путь-к-файлу-в-briefs/>`, зеркало `publish.mjs` (Stage 5, «Путь 1»), но
кладёт объект под префикс `_briefs/<product>/<topicId>.md`, вычисляя
`topicId` из фронтматтера файла, а не из имени файла/папки.

## Дашборд «Синдикация» (добавлено 2026-09-17)

Четвёртая вкладка админки (`tab-syndication`) — рабочее место Stage 7:
готовит и хранит пакеты «тиражируемая версия статьи под конкретную
площадку» отдельно от самой статьи, с собственным заголовком-хуком и
открывающим абзацем (см. «Синдикация» выше, «ремесло хуков для ленты» — не
переносится в оригинал на disrupt-hub.ru, живёт только здесь).

Тот же приём хранения, что у ТЗ — объекты `_syndication/<platform>/
<topicId>.md` в бакете `disrupt-hub-content`, `platform` один из `dzen` /
`vc` / `habr`, без единой правки Cloud Function (валидация та же —
`key.endsWith(".md")`). Список группируется по продукту, теме и площадке;
у одной темы может быть до трёх пакетов (по одному на площадку) — таблица
показывает все параллельно, чтобы было видно, для какой площадки пакет ещё
не готов.

**Редактор пакета** (в отличие от read-only карточки ТЗ — это полноценная
форма, как у статьи): заголовок-хук (отдельно от H1 оригинала), открывающий
абзац-затравка, тело адаптированного текста (markdown, с превью), ссылка на
оригинал в бакете (`originalKey`, только для чтения — берётся из статьи, к
которой готовится пакет), поле «Живая ссылка» (`liveUrl`, заполняется после
фактической публикации на площадке) и статус `draft` → `ready` →
`published`. Памятка с чек-листом площадки (хук из таблицы Stage 7 выше —
для Habr это явное напоминание «только органичный голос, никакого
рекламного тона») показана прямо в редакторе, не только в HUB.md.

Новый пакет заводится кнопкой «+ Синдикация» на вкладке — запрашивает
`topicId`/продукт/площадку, подставляет `originalKey` автоматически, если
статья с этим `topicId` уже есть в бакете (гейт «только после индексации
оригинала» — на совести того, кто создаёт пакет, чекбокс/поле под это не
заведено намеренно, как и для других процессных полей без второго
потребителя — см. принцип в «SEO-поля» ниже).

Публикация с локальной машины — `node admin/scripts/publish-syndication.mjs
<путь-к-файлу-в-syndication/>`, зеркало `publish-brief.mjs`, ключ
вычисляется из фронтматтера (`platform` + `topicId`), не из имени файла.

## Автономное написание статей (2026-09-13)

По прямому запросу Арсения — облачный routine (Claude, запланированный
запуск) сам пишет черновики по уже утверждённым темам и кладёт их в бакет
`disrupt-hub-content` со статусом `qc`, без участия человека в моменте
запуска. Финальный ОК (`published`) по-прежнему только за Арсением — routine
физически не может выставить `published`, только `draft`/`qc` (см. Stage 5,
«Путь 2»).

**Источник контекста — отдельный узкий git-репозиторий**
`git@github.com:arbort/disrupt-hub.git` (приватный), НЕ основная рабочая
среда (`ClaudeVS/` вообще не под git). Содержит только: этот файл, брифы
продуктов для хаба, бэклоги тем, `PRODUCT.md`/`PRODUCTS.md`/`DISRUPT.md`.
Сознательно не содержит креативы, медиапланы, данные кампаний, `admin/`,
`articles/`, секреты — см. `README.md` в самом репозитории. **Этот
git-репозиторий — зеркало на чтение**: правки бэклогов/брифов вносятся в
основном дереве (`/Users/ars/ClaudeVS/disrupt/hub/`), потом `git add` +
commit + push той же командой, что заводила репозиторий — иначе routine
работает по устаревшему контексту.

**Что делает каждый запуск (переписано 2026-09-17 под двухступенчатый гейт
«Семантика вперёд тем» выше — раньше ТЗ существовало только «в уме» одним
проходом с черновиком, теперь материализуется файлом и ждёт отдельного
одобрения):**
1. Читает `hub/HUB.md` целиком (обязательно, как и раньше).
2. Проверяет через `GET <invoke URL>?action=list` (заголовок `X-Admin-Key`)
   текущее состояние бакета: статьи, статус каждой, и объекты `_briefs/*.md`
   с их статусом (`draft`/`approved`).
3. **Сначала черновики по уже одобренным ТЗ** (это не ждёт годами — если ТЗ
   `approved`, значит Арсений уже посмотрел): для каждого `_briefs/<product>/
   <topicId>.md` со статусом `approved`, у которого ещё нет статьи с таким
   `topicId` — если статей в статусе `draft`/`qc` уже ≥ 3-5, пропустить
   (лимит очереди на QC, см. «Жёсткие правила»); иначе написать черновик
   строго по содержанию этого ТЗ (кластер, аутлайн, ключи, конкуренты уже
   зафиксированы — не придумывать заново), с иллюстрациями по конвенции
   Stage 3 (`[SCREENSHOT: ...]` / `[AI-IMAGE: ...]` / `[SETTING: ...]`),
   самопроверкой по чекпойнтам 1-2 Stage 4, публикует через `PUT <invoke
   URL>` с `status: qc` (Stage 5, «Путь 2»).
4. **Затем — новые ТЗ для утверждённых тем без ТЗ**: смотрит
   `hub/topics/*-backlog.md`, ищет темы со статусом **«утверждено»** (не
   «идея» — Гейт 1 не отменён) через `_topics/*.md`-оверрайд ИЛИ git-файл,
   без ещё существующего `_briefs/<product>/<topicId>.md`. Для одной-двух
   таких тем — пишет ТЗ по расширенной структуре Stage 2 (конкуренты через
   WebSearch, таблица ключей с потолком плотности, аутлайн), публикует как
   `_briefs/<product>/<topicId>.md` со статусом `draft`. **Не переходит к
   черновику в этом же прогоне** — это отдельный проход после Гейта 2.
5. Тема, у которой ТЗ уже есть со статусом `draft` (ждёт решения Арсения), —
   пропускается на обоих шагах: routine не дописывает его повторно и не
   начинает черновик без одобрения.

**Приоритет тем — как в разделе «Приоритизация производства» выше**: сначала
Мультитул, потом Тайп, потом остальные. Routine не пишет по темам вне
`topics/*-backlog.md` и не придумывает новые темы сам — Stage 1 (бэклог)
остаётся зоной `hub-writer`/Арсения.

**Разовая настройка, без которой routine не запускается** (сделано 2026-09-13, здесь — чтобы не искать заново при пересоздании):
1. **GitHub App «Claude»** должен быть установлен и дан доступ к репозиторию `arbort/disrupt-hub` — это НЕ то же самое, что просто иметь репозиторий. Ставится на https://github.com/apps/claude → Configure → Only select repositories. Без этого шага `RemoteTrigger create` возвращает `403: You don't have access to a repository this routine uses`, даже если репозиторий существует и SSH-доступ настроен локально — cloud-окружение Anthropic использует отдельный канал авторизации к GitHub, не связанный с локальным `git push`.
2. **Network access окружения должен быть Custom с доменом `functions.yandexcloud.net`.** По умолчанию окружение на уровне **Trusted** — это только реестры пакетов и облачные SDK, Yandex Cloud Functions туда не входит. Без этого шага `curl` внутри routine падает с `connect_rejected (organization policy)`. Настраивается на claude.ai/code → иконка облака у поля ввода → шестерёнка окружения → Network access → Custom → добавить домен в Allowed domains.
3. Оба шага делаются один раз на аккаунт (не на routine) — если понадобится второй routine к другому внешнему API, донастраивать Custom-домены в том же окружении, GitHub App переустанавливать не нужно.
