# HUB.md — Disrupt-Hub: контентный движок

Контекст-файл стрима. Читается целиком агентом `hub-writer` перед любой
задачей. Заведено 2026-09-12 — идея Арсения, согласована с продактом
Дизрапта.

---

## Проблема и идея

Дизрапт-продукты теряют пользователей отчасти потому, что те не знают всех
способностей тулов — не понимают, чем конкретно продукт полезен в их работе
или жизни. Это бьёт по удержанию, а удержание — главный рычаг среднего DAU
(см. `../DISRUPT.md`).

Алиса решает соседнюю задачу ПромптХабом (`alice.yandex.ru/prompthub`), но
только вокруг LLM-части — библиотека промптов, не бизнес-кейсов. Готовых
статей о реальном применении там нет.

**disrupt-hub.ru** — платформа с E2E-статьями и гайдами об использовании
продуктов Дизрапта в реальных рабочих и жизненных сценариях: скрины,
настройки, промпты, а не список функций. Фильтр по продукту. Часть статей —
свой ИИ-движок, часть — публикации пользователей. Лучшее тиражируется во
внешку (Dzen, VC, Habr) через партнёрский подход, который ещё предстоит
согласовать.

**Отличие от ПромптХаба:** не библиотека промптов вокруг одной LLM, а
библиотека кейсов вокруг девяти разных инструментов (десктоп-приложения,
TG-боты, браузерный агент, публичная витрина research-конвейера) — ближе к
связке «блог кастомер-стори + Zapier-style use-case библиотека», чем к
маркетплейсу промптов. Состав — см. «Решения от 2026-09-12» ниже.

| Зона | Кто отвечает |
|---|---|
| Контентный движок: семантика, темы, ТЗ, черновики статей, QC, UGC-модерация, синдикация | **Маркетинг** (Арсений + `hub-writer`) |

## Платформа v1

Исходники — `site/` (Astro, статическая сборка, деплой-ready на Vercel).
Дизайн — язык `deslop` (github.com/mishanaer/deslop): токены скопированы в
`site/src/styles/deslop/`, тёмная тема включена жёстко (не по системной
теме посетителя), что осознанно расходится с правилом «независимый
брендинг» — то правило про рекламные креативы продуктов, для этой публичной
поверхности сделано отдельное исключение решением Арсения.

**Контент не дублируется.** Astro Content Collection (`site/src/content.config.ts`)
читает Markdown прямо из `articles/` этой же папки через `glob()`-loader —
не копия, не symlink. `hub-writer` пишет статьи туда же, куда писал всегда;
рендерится в проде только то, что имеет во фронтматтере `status: published`.

**Обязательный фронтматтер Stage 3** (новое требование к черновику статьи,
без него Astro не соберёт файл в коллекцию):

```yaml
---
title: "Заголовок"
product: tool        # слаг из site/src/data/products.ts
topicId: tool-5        # добавлено 2026-09-13 — "<product>-<номер темы в topics/<product>-backlog.md>"
status: draft         # idea | brief | draft | qc | published
h1: "H1 на странице"
metaTitle: "..."
metaDescription: "..."
date: 2026-09-12
---
```

**`topicId` обязателен с 2026-09-13.** Единственная связь между написанной
статьёй и строкой бэклога — дашборд «Реестр тем» в админке (см. «Админка и
SEO-инфраструктура») сопоставляет их именно по этому полю, не по совпадению
заголовка (заголовок статьи почти всегда переформулирован против темы в
бэклоге). Статья без `topicId` не пропадает — просто попадает в реестре в
раздел «не привязано к бэклогу», и придётся сверять вручную. И `hub-writer`,
и облачная routine обязаны проставлять это поле при написании — для routine
это зашито прямо в её промпт (см. `project_disrupt_hub_autonomous_routine`
в памяти сессии).

**Задеплоено 2026-09-12** на Yandex Object Storage (грант Арсения) —
https://disrupt-hub-deploy.website.yandexcloud.net/. HTTPS работает на
общем домене бакета из коробки. Кастомный домен `disrupt-hub.ru` не
подключён — нужен CDN, отдельный шаг. Передеплой — `npm run deploy` в
`site/`. Полные детали хостинга, что не реализовано (форма UGC, домен) —
`site/README.md`.

## SEO-команда Сбермаркетинга — контекст, не пайплайн

Арсений прощупал платную команду SEO-аналитики Сбермаркетинга. Их обычный
процесс (для справки, хорошая практика сама по себе):

```
разговор о продукте (что раскрывать, что нет)
  → их аналитика и подбор тем → мы утверждаем темы
  → они готовят ТЗ → мы пишем статьи → отправляем на проверку соответствия ТЗ
  → мы публикуем → они проверяют повторно → начинается отслеживание
```

Их урезанное предложение «только по контенту» (без остальных работ по SEO):

- сбор семантики до **20 тем**
- ТЗ на **10–15 текстов**
- мета и H1 к ним
- **итоговая проверка** (соответствие ТЗ)

**Решение:** это предложение в пайплайн не встраивается. Пайплайн ниже
спроектирован как полностью автономный — `hub-writer` сам закрывает
семантику → ТЗ → черновик → QC. Агентство остаётся опцией на будущее:
если понадобится всплеск мощности (например, быстро расширить бэклог сверх
собственных возможностей), к ним можно вернуться на этих же условиях, не
меняя структуру процесса — их ТЗ ложится в тот же формат Stage 2.

Гейт «темы утверждает Арсений до ТЗ» **сохранён** из их процесса — это
хорошая практика вне зависимости от того, кто пишет ТЗ.

**Прецедент из соседнего SEO-контура giga.chat (2026-09-12).** Арсений
прислал реальный рабочий xlsx, который команда SEO giga.chat вела с
агентством 10 месяцев (окт. 2025 — авг. 2026, 253 строки контента + отдельный
лист технических задач). Извлечено и применено к реестру статей (Google Doc):
разведены «URL рекомендованный» и «URL фактический» (SEO-план по слагу почти
всегда расходится с тем, что реально сделал разработчик), статусная лестница
после черновика сделана многоступенчатой (согласовано → размещено → внедрено
— это разные события, не один флаг «опубликовано»), добавлен терминальный
статус «отклонено» с причиной (тема может умереть, не только дойти до
публикации). Сознательно НЕ скопированы колонки «дедлайн», «копирайтер»,
«редполитика», «ТЗ на усиление» — в прецеденте они провисели пустыми весь
срок: не заводить поле под процесс, которого ещё нет.

Лист с техническими SEO-задачами (редиректы, canonical, robots meta, XML
sitemap, микроразметка, перелинковка, Core Web Vitals) сохранён отдельно —
`platform-technical-seo.md` в этой же папке. Это работа для того, кто будет
технически собирать disrupt-hub.ru, не для контентного движка.

## Процесс: восемь стадий

Статус темы движется последовательно. Файлы — в подпапках этой директории.

### 0. Бриф продукта для хаба
`briefing/<slug>-hub-briefing.md`. Что важно раскрывать, что нет — по
аналогии с тем разговором, который в своём процессе первым шагом ставит и
агентство. Разово на продукт, обновляется при крупных изменениях продукта.
Источник фактов — `../shared/PRODUCTS.md` + `../products/<slug>/PRODUCT.md`,
без выдумывания.

### 1. Бэклог тем
`topics/<slug>-backlog.md`. Метод **seed × modifier**: функция продукта ×
реальный сценарий/JTBD × аудитория. Частотность — по Вордстату
(`../shared/wordstat-check.py`), но **не гоним весь бэклог через API
автоматически** — по конвенции среды Вордстат проверяется точечно, по
запросу, для узких/неочевидных формулировок, не валом. До проверки —
`[TBD]`.

**Гейт: темы утверждает Арсений** до перехода на ТЗ.

### 2. ТЗ / бриф статьи
`briefs/<slug>/<topic-slug>-<YYYY-MM-DD>.md`. Кластер интентов (не одно
ключевое слово), intent-тип, формат, H1 + meta title + meta description,
аутлайн с указанием, какой реальный экран/настройка/промпт нужен, внутренняя
перелинковка (на другие статьи хаба + на лендинг продукта), источники фактов
строго из PRODUCT.md/PRODUCTS.md.

### 3. Черновик статьи
`articles/<slug>/<topic-slug>.md`. E2E-статья по ТЗ.

**Конвенция иллюстраций (расширена 2026-09-13).** На каждое место в статье,
которому нужен визуал, — один из двух маркеров, решение за агентом по
принципу «это реальный артефакт продукта или декоративная/пояснительная
картинка»:

- **`[SCREENSHOT: <подробный бриф для человека>]`** — когда нужен настоящий
  экран продукта (это и есть жёсткое правило «без реального артефакта — не
  публикуем», отменить нельзя никаким промптом). Бриф — не одна строка, а
  инструкция, по которой Арсений сможет снять экран не думая: что именно
  открыть, какой ввести запрос/настройку, что должно быть видно в кадре,
  какая тема оформления, что заведомо НЕ должно попасть в кадр (чужие данные,
  реальные ФИО и т.п.). Формат: `[SCREENSHOT: шаги 1) ... 2) ... 3) ...;
  видно в кадре: ...; тема: light/dark; не показывать: ...]`.
- **`[AI-IMAGE: <промпт для генерации>]`** — только для декоративных или
  объясняющих изображений, которые НЕ выдают себя за интерфейс продукта
  (обложка, схема, иконка-метафора). Никогда не заменяет `[SCREENSHOT: ...]`
  там, где смысл абзаца — «вот как это выглядит в продукте». Промпт — сразу
  готовый к вставке в генератор (стиль, композиция, без текста на картинке,
  без брендинга Сбера — независимый брендинг).

Оба маркера — не выдумка контента, а поручение: агент никогда не описывает
внутри статьи то, чего не видел (никаких «на скриншоте видно, что...» до
того, как скриншот появится).

`[SETTING: описание]` — для описания конкретной настройки продукта текстом
(не изображение), используется как раньше.

### 4. QC — три чек-пойнта
1. Соответствие ТЗ (кластер покрыт, H1/meta на месте, формат соблюдён)
2. Продуктовые факты и бренд-правила (независимый брендинг, запреты по
   продуктам — мед. заявления Айвы, этика звонка Консьержа, размежевание
   Ники и Консьержа по механике, а не по задаче)
3. Пост-паблиш техничка (мета/H1 живые на сайте, ссылки резолвятся) — после
   публикации dev-командой

Финальный ОК — **только Арсений**. Агент не самоапрувит.

### 5. Хэндофф на публикацию
**Изменено 2026-09-13, с появлением админки (см. «Админка и SEO-инфраструктура»
ниже).** Сайт больше не читает `articles/` напрямую — источник Astro-коллекции
теперь `articles-published/`, зеркало бакета `disrupt-hub-content`. Просто
поменять `status` в локальном файле `articles/<slug>/` больше не публикует
его — файл должен физически попасть в бакет. Статус после хэндоффа — **`qc`**,
не `published`: Финальный ОК остаётся только за Арсением (см. Stage 4), пуш в
бакет лишь делает черновик видимым и редактируемым в админке.

**Путь 1 — локально (Claude Code на машине Арсения):** запустить `node
disrupt/hub/admin/scripts/publish.mjs <путь-к-файлу>` — скрипт кладёт файл в
бакет через Cloud Function (с проверкой ETag, чтобы не перезаписать
параллельную правку из веб-админки). Секрет — в `admin/scripts/.env.local`
(untracked), агент его не видит и не должен искать.

**Путь 2 — облачный routine (автономный, без Claude Code на месте).** У
routine нет доступа к локальным файлам и `.env.local` — вместо `publish.mjs`
он делает прямой HTTP-запрос к той же Cloud Function: `PUT <invoke URL>`,
заголовок `X-Admin-Key: <ADMIN_SECRET>` (передан в промпте routine, не
хранится в git), тело `{"key": "<product>/<slug>.md", "raw": "<полный текст
файла с фронтматтером>"}`. Перед тем как писать новую статью, routine
обязан проверить `GET <invoke URL>?action=list` с тем же заголовком и
посчитать, сколько статей сейчас в статусе `draft`/`qc` (ещё не
`published`) — если ≥ 3-5 (см. «Жёсткие правила», темп ограничен проверкой),
в этот прогон новых статей не добавлять.

### 6. UGC
Чек-лист модерации (бренд-safety, без выдуманных фич, реальный E2E, не спам)
+ меню стимулов, `ugc/incentives.md`. Форма приёма статей от пользователей —
зона дева, агент её не проектирует, только пишет критерии и лог.

### 7. Синдикация
`syndication/<slug>/<topic-slug>-syndication.md`. Только после индексации
оригинала на disrupt-hub.ru, с лагом. Копия адаптируется под площадку, не
копипастится:

| Площадка | Тон |
|---|---|
| Dzen | ближе к оригиналу, RU-нативная площадка |
| VC | подаётся как инсайт/личный опыт команды, не как пресс-релиз |
| Habr | **только органичный голос команды**, никакого рекламного тона — лессон уже зафиксирован в `../shared/channels.md` |

## Расширение аналитических конвенций

- **UTM** (`../shared/utm.md`): `utm_source=disrupt_hub` для самой площадки,
  `utm_source=dzen` / `utm_source=vc` для синдикации (`habr` уже
  зарезервирован), `utm_medium=content` или `organic`, `utm_campaign=
  <product>_hub_<период>`.
- **События** (`../shared/events.md`): `hub_article_view`, `hub_cta_click`
  (переход статья → продукт), `ugc_submit`.

  органические сессии, CTR статья→продукт, число UGC-заявок.

## Жёсткие правила

- **Без реального артефакта продукта — не публикуем.** Ни одна статья не
  выходит только на общих советах: это ровно то, что Google квалифицирует
  как scaled content abuse.
- **Не выдумывать продуктовые факты.** Экраны, настройки, цифры — только из
  PRODUCT.md/PRODUCTS.md или реальной съёмки. Нет — плейсхолдер, не догадка.
- **Независимый брендинг.** Правила режима A (палитра GigaChat, SB Sans) к
  хабу не применяются, если только сайт не решит иначе на своей стороне —
  это не зона контентного движка.
- **Продуктовые запреты не отменяются потому, что это SEO-контент**: Айва —
  без диагнозов и гарантий результата, с дисклеймером «не заменяет
  консультацию врача»; Консьерж — без захода в этическую рамку звонка;
  Ника/Консьерж — сценарии разводятся по механике (онлайн-путь vs звонок),
  не по задаче, чтобы статьи не сталкивали продукты лбами в одной выдаче.
- **Синдикация не раньше индексации оригинала**, с лагом. Habr — только
  органичный голос команды.
- **Тёмп ограничен проверкой, не генерацией.** Дефолт — не больше 3–5
  черновиков в очереди на QC одновременно у Арсения; корректируется по факту
  реальной пропускной способности.
- **Числа — с источником.** Частотность, охват, конверсии — из выгрузки или
  Вордстата по конкретному запросу, иначе `[TBD]`.

каждый). Арсений задал распределение усилий контентного движка при
переходе тем в работу (Stage 2 и далее):

| Доля | Продукт(ы) |
|---|---|
| **70%** | Мультитул (`tool`) |

первыми, и в чей слот QC (не больше 3–5 черновиков одновременно, см.

затем — по одной-две темы за проход из оставшихся семи, начиная с
ИИ-Консьержа.

собственной фактурой: у всех пяти PRODUCT.md — стаб с лендинга, без брифа
Дизрапта (см. «Решения от 2026-09-12»). Даже в пределах отведённых 10%
это дополнительно тормозит переход в Stage 2 до появления более полной
фактуры или до explicit-решения Арсения писать по тому, что есть.

## Админка и SEO-инфраструктура (2026-09-13)

Арсений явно попросил веб-админку статей с редактором и SEO-чеклистом,
явно выбрал хостинг на собственном Yandex Cloud (не Claude Artifact — там
CSP блокирует произвольный fetch к внешним API), и явно попросил широкий
чеклист по образцу процесса SEO-команды giga.chat.

**Хранилище и разделение с рабочей папкой hub-writer.** Новый бакет
`disrupt-hub-content` — канонический источник статей (`.md` с тем же
фронтматтером). Новая директория `disrupt/hub/articles-published/` —
зеркало этого бакета, и только зеркало; `content.config.ts` теперь читает
её, а не `articles/`. `articles/` (рабочая папка `hub-writer` для
idea/brief/draft/qc) не тронута специально: `npm run sync-content`
использует `aws s3 sync --delete`, и если бы он синхронизировал `articles/`
напрямую, любой локальный черновик, который ещё не попал в бакет, был бы
удалён при первом же деплое, случившемся во время работы `hub-writer`. Два
каталога = два владельца, ноль пересечения по умолчанию.

**Cloud Function публичная, не приватная.** Первая идея — приватная функция
+ API-ключ — не работает: браузерный CORS-preflight (`OPTIONS`) никогда не
несёт кастомный `Authorization`, а Yandex режет приватную функцию без него
ещё на уровне платформы, до кода. Функция публичная
(`allow-unauthenticated-invoke`), `OPTIONS` отвечает `204` без проверки,
`GET/PUT/DELETE` сверяют заголовок `X-Admin-Key` с `ADMIN_SECRET` в коде —
тот же по силе bearer-secret, что и API-ключ, без второго сервис-аккаунта и
без проблемы preflight. Доступ к бакету — статический access key отдельного
сервис-аккаунта `disrupt-hub-content-sa` (роль `storage.editor`, только этот
бакет) в переменных окружения функции. Код — `disrupt/hub/admin/function/`.

**Публикация ≠ деплой сайта.** Сохранение/публикация в админке (или через
`publish.mjs`) кладёт файл в `disrupt-hub-content` — не пересобирает и не
выкатывает сайт. `npm run deploy` (теперь `sync-content && astro build && aws
s3 sync ...`) остаётся ручным шагом «выкатить в прод», как и раньше.

**SEO-поля — что реально добавлено в схему, а что нет.** Тест: есть ли в
этой же задаче реальный потребитель поля. `canonical` (переопределение,
по умолчанию считается из пути файла), `ogImage`, `robots`, `schemaType`
(`Article`/`HowTo`) — да, `BaseLayout.astro`/`[slug].astro` их рендерят →
добавлены в Zod-схему `content.config.ts`. «Широкие» giga.chat-поля
процесса (дедлайн, копирайтер, редполитика) — **сознательно не добавлены**:
живого потребителя нет (один автор — `hub-writer`, ни календаря, ни второй
роли), а это ровно тот же принцип «не заводить поле под процесс, которого
ещё нет», который уже был записан в этом файле раньше — не повторяем его же
нарушение в схеме. «Широкое» ревью реализовано иначе: в самой админке есть
три сессионных чекбокса (ТЗ в `briefs/`, бренд-правила, 3 QC-чекпойнта),
которые блокируют выбор статуса `published`, пока не отмечены — ничего из
этого не пишется в файл, поэтому не может стать мёртвым грузом.

Заодно закрыты несколько пунктов `platform-technical-seo.md` в коде сайта:
`rel=canonical`, `meta robots`, Open Graph/Twitter, JSON-LD (Article/HowTo),
XML sitemap (`@astrojs/sitemap`), блок «похожие статьи» того же продукта на
странице статьи (перелинковка — источник называл её «без этого краулер
почти не доходит до статей»). Не закрыто: редиректы, Core Web Vitals —
вне фазы 1, см. `platform-technical-seo.md`.

**Вне фазы 1, явно:** загрузка изображений (плейсхолдеры `[SCREENSHOT: ...]`
остаются), rich-редактор (только textarea + markdown-превью), мультипользо-
вательские роли, история версий/откат, автодеплой сайта по факту публикации,
API Gateway/кастомный домен для функции, Lockbox для секретов (пока —
переменные окружения функции).

**Ручная настройка Yandex Cloud завершена и проверена 2026-09-13** (сервис-
аккаунт, статический ключ, функция, переменные окружения, `.env.local`) —
подробности и живые адреса в `site/README.md`, раздел «Админка». Обнаружено
и исправлено в процессе: (1) функция вернула бы 500 вместо 404 на запрос
несуществующей статьи — правило конфликтов `publish.mjs` на это опиралось;
(2) первая версия `publish.mjs` сверяла etag со свежим GET прямо перед
своим же PUT, из-за чего конфликт никогда не мог сработать — тихая
перезапись правки из веб-админки была обнаружена вручную и закрыта
локальным файлом состояния `.publish-state.json`; (3) автосоздание версии
функции по ссылке на объект в Object Storage дважды ломалось необъяснимо —
рабочий путь оказался только ручной загрузкой ZIP через консоль.

**Дашборд «Реестр тем» (добавлено 2026-09-13).** Арсений заметил, что
админка показывала только написанные статьи (2 шт.) и не давала увидеть
весь бэклог из 90 тем — сколько утверждено, сколько ещё «идея», по каким
продуктам вообще ничего не одобрено. Новая вкладка в админке
(`admin/web/index.html`, кнопка «Реестр тем») сводит `topics/*-backlog.md`
(источник статусов «идея»/«утверждено») со списком реальных статей из
Cloud Function (`?action=list`) в одну таблицу: сводка по продуктам (тем /
утверждено / написано / опубликовано), фильтры по продукту и статусу,
кнопка «Открыть →» на написанные, отдельный блок для статей без `topicId`
(«не привязано к бэклогу»).

Сознательное архитектурное решение — **не трогать Cloud Function**. Её
деплой — единственное по-настоящему хрупкое звено всей админки (см. выше:
только ручная загрузка ZIP через консоль, автосоздание версии по ссылке на
объект дважды ломалось необъяснимо). Вместо нового эндпоинта — статический
`admin/web/data/topics.json`, генерируемый локальным скриптом
`node admin/scripts/sync-topics.mjs` (парсит все `topics/*-backlog.md` по
именам колонок в заголовке таблицы, не по фиксированной позиции — у
`aiwa-backlog.md` на одну колонку больше остальных) и заливаемый вместе с
остальной статикой админки обычным `npm run deploy:admin` — ни единой
строчки в `admin/function/`. **После любой правки статусов в
`topics/*-backlog.md` дашборд не обновится сам** — нужно руками прогнать
`sync-topics.mjs` и передеплоить `admin/web/` тем же `deploy:admin`.

Связь «написанная статья ↔ строка бэклога» — новое обязательное поле
`topicId` во фронтматтере (см. пример фронтматтера выше). Задним числом
проставлено двум уже существовавшим статьям (`tool-1`, `tool-5`) прямым PUT
через Cloud Function. Промпт автономной routine (см. ниже) обновлён
2026-09-13 тем же днём: обязана проставлять `topicId` и сверять дубликаты
по нему, а не по тексту заголовка.

**Одобрение темы прямо из дашборда (добавлено 2026-09-13, тем же днём).**
Арсений попросил менять статус темы «идея → утверждено» прямо в реестре, а
не редактируя `topics/*-backlog.md` руками — чтобы облачная routine сразу
подхватила тему на следующий прогон. Источник правды для статуса темы
остаётся `topics/*-backlog.md` в git (оба места — локальная копия и
зеркало `arbort/disrupt-hub` — не переписываются кнопкой «Утвердить»), но
поверх него введён **живой слой оверрайдов**: кнопка кладёт в тот же бакет
`disrupt-hub-content` крошечный `.md`-объект `_topics/<topicId>.md` с
фронтматтером `{topicId, status}` — снова без единой правки Cloud Function,
объект просто проходит существующую валидацию PUT (`key.endsWith(".md")`).
`?action=list` неизбежно возвращает эти объекты вперемешку с настоящими
статьями — отфильтрованы из списка статей и «сирот» на клиенте по префиксу
`_topics/`, различить статью и оверрайд можно и по полям (у статьи есть
`title`, у оверрайда — только `topicId`+`status`).

Приоритет статуса темы в реестре: **написанная статья > живой оверрайд >
статус из git-файла**. Кнопка «Вернуть в идею» удаляет оверрайд (DELETE),
после чего тема просто показывает то, что написано в git-файле — если там
и так «утверждено», кнопки нет вообще (нечего откатывать через дашборд, это
меняется только в файле). Тема со статусом «идея — блокировано» кнопки
«Утвердить» не получает — блокировка продуктового/юридического вопроса не
должна сниматься одним кликом мимо разбора, который её туда поставил.

Промпт routine обновлён снова тем же днём: гейт «утверждено» теперь
выполняется по ИЛИ — git-файл ИЛИ живой оверрайд в бакете, дубликаты и лимит
очереди по-прежнему считаются только по настоящим статьям (объекты
`_topics/*.md` явно исключены из подсчёта). Живой оверрайд НЕ переносится
обратно в git-файл автоматически — при генеральной уборке бэклога стоит
сверить `_topics/*.md` в бакете с `topics/*-backlog.md` и снести те
оверрайды, для которых статья уже написана (дальше они не нужны, приоритет
"написанная статья" их и так перекрывает, но за место в бакете и лишний
`GetObject` в `?action=list` не платить смысла нет).

## Автономное написание статей (2026-09-13)

По прямому запросу Арсения — облачный routine (Claude, запланированный
запуск) сам пишет черновики по уже утверждённым темам и кладёт их в бакет
`disrupt-hub-content` со статусом `qc`, без участия человека в моменте
запуска. Финальный ОК (`published`) по-прежнему только за Арсением — routine
физически не может выставить `published`, только `draft`/`qc` (см. Stage 5,
«Путь 2»).

**Источник контекста — отдельный узкий git-репозиторий**
`git@github.com:arbort/disrupt-hub.git` (приватный), НЕ основная рабочая
среда (`ClaudeVS/` вообще не под git). Содержит только: этот файл, брифы
продуктов для хаба, бэклоги тем, `PRODUCT.md`/`PRODUCTS.md`/`DISRUPT.md`.
Сознательно не содержит креативы, медиапланы, данные кампаний, `admin/`,
`articles/`, секреты — см. `README.md` в самом репозитории. **Этот
git-репозиторий — зеркало на чтение**: правки бэклогов/брифов вносятся в
основном дереве (`/Users/ars/ClaudeVS/disrupt/hub/`), потом `git add` +
commit + push той же командой, что заводила репозиторий — иначе routine
работает по устаревшему контексту.

**Что делает каждый запуск:**
1. Читает `hub/HUB.md` целиком (обязательно, как и раньше).
2. Смотрит `hub/topics/*-backlog.md`, ищет темы со статусом **«утверждено»**
   (не «идея» — гейт Stage 1→2 не отменён, routine не трогает
   неутверждённые темы).
3. Проверяет через `GET <invoke URL>?action=list` (заголовок `X-Admin-Key`),
   сколько статей уже в статусе `draft`/`qc` — если ≥ 3, в этот прогон
   новых тем не берёт (темп ограничен проверкой, не генерацией).
4. Для одной-двух утверждённых тем без черновика: пишет ТЗ-уровня разбор
   в уме (Stage 2 не обязательно материализовать отдельным файлом для
   routine — контекста нет для брифов, если их не завести в репозитории
   контекста), сам черновик с иллюстрациями по конвенции Stage 3
   (`[SCREENSHOT: ...]` / `[AI-IMAGE: ...]` / `[SETTING: ...]`),
   самопроверку по чекпойнтам 1-2 Stage 4.
5. Публикует через `PUT <invoke URL>` с `status: qc` (Stage 5, «Путь 2»).

**Приоритет тем — как в разделе «Приоритизация производства» выше**: сначала
Мультитул, потом Тайп, потом остальные. Routine не пишет по темам вне
`topics/*-backlog.md` и не придумывает новые темы сам — Stage 1 (бэклог)
остаётся зоной `hub-writer`/Арсения.

**Живая инфраструктура (задеплоено и проверено 2026-09-13):**

**Разовая настройка, без которой routine не запускается** (сделано 2026-09-13, здесь — чтобы не искать заново при пересоздании):
1. **GitHub App «Claude»** должен быть установлен и дан доступ к репозиторию `arbort/disrupt-hub` — это НЕ то же самое, что просто иметь репозиторий. Ставится на https://github.com/apps/claude → Configure → Only select repositories. Без этого шага `RemoteTrigger create` возвращает `403: You don't have access to a repository this routine uses`, даже если репозиторий существует и SSH-доступ настроен локально — cloud-окружение Anthropic использует отдельный канал авторизации к GitHub, не связанный с локальным `git push`.
2. **Network access окружения должен быть Custom с доменом `functions.yandexcloud.net`.** По умолчанию окружение на уровне **Trusted** — это только реестры пакетов и облачные SDK, Yandex Cloud Functions туда не входит. Без этого шага `curl` внутри routine падает с `connect_rejected (organization policy)`. Настраивается на claude.ai/code → иконка облака у поля ввода → шестерёнка окружения → Network access → Custom → добавить домен в Allowed domains.
3. Оба шага делаются один раз на аккаунт (не на routine) — если понадобится второй routine к другому внешнему API, донастраивать Custom-домены в том же окружении, GitHub App переустанавливать не нужно.
